## 1. 배경 — 왜 필요한가

- 원 요청(사용자 브레인스토밍): 홈 화면 주간 ToDo, 기업·동종업계 데이터를 본 AI 맞춤
  실천 방안, 실천 체크 시 성취감 요소, 참고 데이터로 탄소중립포인트제 같은 공식
  실천 방안 사용.
- 코드 조사 결과 확인된 공백: 현재 체크리스트(`GoalCard.tsx`의 `missing_items`,
  `document_requirements.py`의 필수서류 안내)는 전부 **"측정하기 위한 할 일"**
  (고지서 더 올리기)이다. **"감축하기 위한 할 일"은 어디에도 없다.**
- 이 문서 작성 전 검토했다가 기각한 대안(문서 하단 §9 참고): 외부 실천 방안
  카탈로그를 1차 콘텐츠 소스로 쓰는 안. 탄소중립포인트제(`cpoint.or.kr`)는 가정용
  8개 항목뿐이고 업종 특화 콘텐츠가 없었다(실사이트 확인, 2026-08-25). 한국에너지공단
  KEEP+ 안내자료(2023, 13p)도 보조사업 신청 안내일 뿐 절감률 사례집이 아니었다.
  콘텐츠 조달이 병목이라는 결론에 도달해, **외부 카탈로그 없이 감탄 자신의 데이터로
  액션을 만드는 방향**으로 선회했다.

## 2. 핵심 원칙 — LLM은 문장만, 판단은 전부 코드

CLAUDE.md §5 원칙1("LLM 산수 금지")을 이 기능에도 그대로 적용한다. 선례:
`db/document_llm_router.py`(LLM은 셀 id만 고르고 값은 정규식 재파싱),
`db/owner_briefing.py`(숫자는 코드가 계산, LLM은 문단만 조립, 실패 시 템플릿 폴백).

이 기능의 4단계 파이프라인:

1. **진단 (코드)** — 이 기업의 연료별 사용 패턴, 최저 사용월(기준부하), 매칭된 설비
   신호를 계산. 개인화의 대부분이 여기서 나온다.
2. **매칭 (룰)** — 카탈로그 액션의 `trigger` 조건에 진단값을 대입해 통과한 액션만
   추린다.
3. **효과 계산 (코드)** — 기준부하 대비 목표치, 절감 예상량을 결정론적 함수로 계산.
4. **문장 다듬기 (LLM, 선택)** — 여러 액션이 통과했을 때 우선순위·톤만 조정. 응답
   스키마에 숫자 필드를 두지 않는다 — 실패해도 3단계 결과만으로 카드가 완결된다
   (아래 §7 참고).

**안전장치 2개 (카탈로그 스키마 자체에 강제):**

- `trigger` 조건 미충족이면 그 액션은 목록에 아예 없다 — 모든 기업에게 같은 액션이
  뜨는 걸 막는다.
- **`verify_metric`이 없는 액션은 카탈로그에 등록할 수 없다.** "직원 교육 하세요"류
  검증 불가능한 액션이 원천적으로 걸러진다. 이건 나중에 추가하는 게 아니라 카탈로그
  스키마 설계 시점부터 강제한다.

## 4. 정정된 사실 — "FK009/FK010 재활용"은 틀린 전제였다

이전 논의에서 "이미 돌고 있는 `facility_keywords`(FK001~FK010)를 재활용한다"고
전제했으나, **코드 조사로 확인한 실제 그림은 다르다**:

- `facility_keywords` 엑셀 시트(FK001~FK009, **FK010 없음, 총 9개**)는 실존하지만
  **이걸 읽는 코드가 없다.** DB 테이블도, 로더 함수(`db/excel_loader.py`)도 없다.
  Excel 원본 확인 결과 이 시트는 `k_taxonomy_mapping`(KT001~KT009)의 요약/중복
  버전이다 — `keyword`·`default_lead_type` 등 컬럼이 KT 시트와 1:1 대응한다.
- **실제로 매 전표마다 도는 건 `api/agent/rules.py::match_rule()`**이고, 이게 엑셀
  `분류_기준표_확장` 시트의 R031/R032/R051~R058(K택소노미 관련 9개 룰)을 포함한
  50개 룰 전체를 순회한다.
- 이전 논의의 "FK009 유지보수·FK010 수리비" 언급은 실제로는 **`R058`("설비
  유지보수비", 포함키워드 "유지보수비/유지보수/정기점검", `자동처리="사람검토"`,
  `정답Scope="검토"`, 판단기준: "신규 설비투자인지 단순 수리인지 불명확")**이었다.
  R058은 `k_taxonomy_mapping` 시트에 매핑 행이 없다 — `finance_lead_type`이
  안 채워지므로 은행 리드 목록(`k_taxonomy_leads()`)에서 조용히 빠진다. 이게
  "지금 검토필요로 버려지는 신호"의 정체다.
- **결정(사용자 확인, 2026-08-25): 새 데이터 테이블을 만들지 않는다. 기존 룰 엔진
  (`rules.py`) 위에 감축 트리거를 추가하는 방향으로 간다.** 구체적으로는 R058 같은
  "설비투자 불명확" 룰이 매칭된 Classification을 감축 트리거의 "노후 설비 의심"
  신호로 재해석한다.

### 4.1 남은 스키마 갭 — `rule_id`가 저장되지 않는다

`Classification`(`db/models.py:72`)에는 `k_taxonomy_candidate_type`,
`k_taxonomy_facility_type`, `finance_lead_type` 컬럼은 있지만 **`rule_id` 자체를
저장하는 컬럼이 없다.** R058처럼 `k_taxonomy_mapping`에 매핑이 없는 룰(즉
`finance_lead_type`이 null인 케이스)은 매칭 후 `category`(R058의 경우
"설비투자 불명확")와 `evidence`(근거 문장, 룰 파일이 채우는지 확인 필요) 외에는
"어떤 룰이 매칭됐는지" 알 방법이 남지 않는다.

**확정(2026-08-25, 실측 재확인 — 아래 두 가지가 순서대로 틀렸다가 바로잡힘)**:

1차 시도: `api/agent/tools.py::_rule_decision()` 89행의
`evidence = f"[{rule['rule_id']}] {rule['reasoning']}"`(룰 경로 전용, `[R058]`
접두사)로 식별하려 했으나, **R058은 이 경로를 타지 않는다.** R058의
`auto_action`이 "사람검토"인데 `_SHORT_CIRCUIT_ACTIONS = ("자동분류", "자동제외",
"참고분류")`에 "사람검토"가 없어, R058이 매칭돼도 `_rule_decision()`은 결정을
확정하지 않고 항상 **LLM으로 위임**한다(`rule_hint`로만 넘김). 이 사실은
`GEMINI_API_KEY` 없이 직접 실행해 `method == "llm"`으로 떨어지는 걸 실측
확인했다(테스트 실행 중 발견, 2026-08-25) — 즉 룰 경로 포맷은 R058엔 애초에
적용되지 않는다.

**최종 확정**: LLM 경로의 `_llm_result_to_decision()`(`tools.py:192`)이
`rule_hint.get("needs_review")`가 참일 때
`evidence = f"{llm_reason} — 회계 룰상 사람검토 필요(참고: {rule_hint['rule_id']})"`
형태로 **룰 ID를 문장 끝에 접미사로** 남긴다. 따라서 식별 조건은
`Classification.evidence LIKE '%(참고: R058)%'`이다(부분일치 — LLM이 만드는
앞부분 문장은 매번 달라짐). `method` 필터는 두지 않는다(R058은 항상 llm이므로).
스키마 변경(Alembic revision)은 이번에도 불필요 — evidence 컬럼 파싱만으로
충분하다. 구현·테스트는 `db/pcaf_engine/reduction_actions.py::aging_equipment_signal()`,
`tests/pcaf_engine/test_reduction_actions.py` 참고.

## 5. 3층 설계

### 5.1 1층 — 어느 연료를 볼지 결정

- 입력: `Company.industry_code`, `employee_count`
- `api/queries.py::get_distribution()` 재사용 — 업종·규모 대비 이 기업이 어느
  Scope/연료에서 상대적으로 높은지만 판단. **액션 선택에는 쓰지 않는다** — "어느
  연료를 진단 대상으로 좁힐지"까지만.

### 5.2 2층 — 설비 신호 (전표 품목 텍스트 = 설비 인벤토리 대용)

- 입력: 해당 기업의 `Classification` 중 `k_taxonomy_facility_type IS NOT NULL`
  (기존 K택소노미 매칭 결과, 새로 만들지 않음) + `evidence LIKE '%(참고: R058)%'`
  (§4.1 확정 방식으로 식별 — R058은 항상 LLM 경로이므로 method 필터 없음) 건.
- 이 두 신호를 합쳐 "이 기업엔 어떤 설비가 있고, 그중 노후 의심 신호가 있는가"를
  판단. 예: 지게차(`k_taxonomy_facility_type == "전동지게차"`가 없는데 "지게차"
  키워드가 Scope1 경유 분류로 잡힘)는 "구형 지게차 보유"로, R058 매칭 건은
  "노후 설비 의심"으로 트리거에 넣는다.
- **한계 (원문 그대로 인정)**: 고지서(전기·가스)만 있고 세금계산서가 없는 기업은
  이 층이 안 돈다 — 설비 신호 자체가 없다. **이건 액션이 줄어드는 게 맞다.** 다만
  액션이 0개가 되는 걸 막기 위해 §6 폴백을 반드시 둔다.

### 5.3 3층 — 시계열 분해 (1차 스코프는 기준부하만)

- **1차: 기준부하 추정** — `monthly_by_fuel()`로 얻은 연료별 월별 활동량에서
  최근 12개월(`_trailing_months()`와 같은 패턴) 중 최저값을 "이 기업이 보여준
  최선의 달"로 삼는다. 목표 문구: "OO월 수준(X)으로 돌아가면 연간 Y톤 절감".
  화면에는 **반드시 "추정"이라고 표기한다**(원문 요구사항, 월 단위 최저값이라
  일회성 저사용월일 수 있음 — 확정치처럼 보이면 CLAUDE.md §5 원칙10 위반 소지).
- **2차(§8로 이연): 원단위 추이(매출 대비)** — `borrower_financials` 연계, 금액/
  물량 분리(`unit_prices` 월별). 재무 데이터 품질 의존도가 높고 계산 로직이
  복잡해 1차에서는 제외.

## 6. 폴백 — 액션 0개 화면을 만들지 않는다

2층 신호가 없는 기업(고지서만 있는 경우)을 위해, 1층(업종) 기준의 **최소 일반
액션 2~3개를 카탈로그에 고정 등록**해 항상 최소 1개는 뜨게 한다. 콘텐츠 출처는
탄소중립포인트제 공식 사이트 확인 결과(2026-08-25 fetch) 중 사업장에도 적용
가능한 3개만 채택:

| 액션 | 원문 수치 (가정 기준, 참고용) |
| --- | --- |
| 냉난방 온도 1℃ 조정 | 연간 CO₂ 110kg, 비용 34,000원 절감 |
| 절전형 조명 교체(백열→형광) | 연간 CO₂ 17kg 절감 |
| 대기전력 차단 | 대기전력이 전체 사용 전력의 약 10% |

이 3개는 `verify_metric`을 못 만든다(전등 교체 여부를 감탄이 확인할 방법이 없음)
— **§2의 "verify_metric 없으면 등록 불가" 원칙과 충돌한다.** 따라서 이 3개는
카탈로그 정식 액션이 아니라 **"검증 없는 참고 팁"으로 분리해 별도 UI 섹션**에
둔다(예: "이런 것도 도움이 돼요" 캡션, 체크리스트에는 안 넣음). 정식 감축
목표(체크 가능·검증 가능)는 항상 §5.3의 기준부하 계산에서만 나온다.

  제도로 흘린다(§9.2 참고).

## 11. 재설계 — 숫자 카드에서 동사형 할 일로 (2026-08-25)

1차 구현을 실제 화면에 붙여보고 나온 문제:

```
경유/유류 10월 수준으로 돌아가면        0.02tCO2e 절감
예상치예요 · 12월 0.23tCO2e → 10월 수준 0.21tCO2e
```

사용자 피드백 — "이건 필요없어보이는데 다른 데이터 없어?" → "뭔가 이번주
할일이라는 느낌이 아니잖아" → "단순하게 뭐 하세요가 될거같아서". 핵심 진단:
**계산은 맞았지만 형식이 틀렸다.** 3층(기준부하)이 만드는 건 결과 지표(숫자)이지
행동(동사)이 아닌데, 그걸 그대로 "이번주 할 일"의 메인 콘텐츠로 냈다. 절감량이
작을 때(0.02tCO2e) 특히 이 문제가 두드러졌지만, 근본 원인은 절감량 크기가
아니라 애초에 숫자 카드가 "할 일"이 될 수 없다는 형식 문제였다.

### 11.1 새 구조 — todos가 메인, goals는 배경

응답에 최상위 필드 `todos`(동사형 할 일 문장)를 추가했다. 기존 `goals`(3층
숫자)는 계산 로직·필드 구성 그대로 유지하되, 화면에서 todos 아래 작은 배경
정보(`ReductionGoalBackground`, 옅은 톤·구분선 아래)로 물러난다. `tips`
필드는 없어지고 `todos`에 흡수됐다(FALLBACK_TIPS는 그대로 존재, `_tip_todos()`
가 todos 형태로 변환할 뿐).

동사형 문장은 두 소스에서 온다:
- **2층 설비 신호 → 동사형 변환**: `_FACILITY_TODO_HINTS`가 기존
  `_FACILITY_REASON_HINTS`(설명형, "~일 수 있어요")와 짝을 이루는 행동형
  문장("~확인해보세요", "~점검해보세요")을 제공. 같은 설비 신호가 goals의
  이유 문구(설명형)와 todos의 할 일 문장(행동형) 양쪽에 다른 문형으로 쓰인다.
- **FALLBACK_TIPS → 그대로**: 설비 신호가 없을 때(2층이 안 도는 기업) 폴백.

### 11.2 사업 규모 분기 — "만약 소상공인이면?"

사용자 질문으로 소상공인 케이스를 짚어보니 두 가지가 확인됐다:
1. 소상공인은 세금계산서보다 전기·가스 고지서 위주라 2층(K택소노미 설비
   키워드)이 원래 잘 안 잡힌다 — 화면에 뜬 "전기/경유·유류"만 나온 것도 이
   증상일 수 있다.
2. 소상공인에게는 이미 **탄소중립포인트 트랙**(`db/carbon_neutral_point.py`)
   이 같은 "전기 아끼기" 메시지를 감축률·환급액으로 다루고 있다. 여기서 새
   감축률을 또 계산하면 같은 기업에 대해 서로 다른 숫자를 내는 두 계산기가
   생겨 CLAUDE.md §5 원칙10과 충돌할 소지가 있다.

**확정(2026-08-25)**: 소상공인(`business_scale_hint == "소상공인/상업시설"`)은
설비 신호가 있어도 **항상 FALLBACK_TIPS를 메인 todos로 쓴다** — 설비 기반
문장을 아예 만들지 않는다(단순히 우선순위를 낮추는 게 아니라 분기 자체에서
배제). 이 모듈은 소상공인의 감축률·환급액을 **다시 계산하지 않는다** —
`business_scale_hint`(값만)를 응답에 반환해, 프론트가 필요하면 이미 있는
`getCarbonPointEligibility()`/`CarbonPointCard`와 조합하게 한다(연결은 이번
스코프에서 구현하지 않음 — 필드만 노출, 실제 화면 연결은 2차 스코프 후보).

`business_scale_hint` 자체는 `db/carbon_neutral_point.py::business_scale_hint()`
를 그대로 호출한 값이다(새 판정 로직 없음) — 전기고지서 계약종별 기반, 이미
탄소중립포인트 트랙이 쓰는 것과 동일한 함수.

## 12. 실제 DB 데이터 공백 발견 및 수정 (2026-08-25)

재설계(§11) 후 실사용 화면에서 "구미정밀"·"대경부품" 둘 다 설비 신호(2층)
없이 폴백(todos)만 뜨는 게 확인됐다. 사용자 질문 — "현재 제조업들은 설비
신호 매칭이 왜 안돼?" → "k 택소노미는 어디에 쓰이게돼?"

### 12.1 원인 — 두 개의 서로 다른 합성 전표 생성기

- `db/synth_dataset_generator.py`: 엑셀 워크북(`data/감탄_데이터준비_샘플.xlsx`)
  을 만드는 기획 참고 자료 생성기. "태양광 설비 설치"(C002 대경부품),
  "전동지게차 리스료"(C003 성서테크) 같은 K택소노미 예시가 있지만 **DB에
  적재되는 경로가 아니다.**
- `db/synth_generator.py`(실제로 DB에 전표를 채우는 생성기, `db/scenarios.py`
  가 호출): `FUEL_EXPRESSIONS`가 경유·도시가스·전기 **3연료만** 다룬다.
  태양광·전동지게차·고효율설비 등 K택소노미 어휘가 애초에 없다.

실측(Supabase 개발 DB 직접 조회, 2026-08-25): 9개 회사 중 8곳이
`k_taxonomy_facility_type` 매칭 0건. "임시기업"(테스트 흔적으로 추정) 1곳만
1건.

### 12.2 영향 범위 — 감축 ToDo만의 문제가 아니었다

K택소노미(`Classification.k_taxonomy_facility_type`/`finance_lead_type`)를
실제로 쓰는 곳 4곳이 전부 이 공백의 영향을 받고 있었다:
1. 은행 담당자 화면 — 설비금융 리드 목록(`k_taxonomy_leads()`)
2. 사장님 화면 — 설비금융 안내 카드(`KTaxonomyCard.tsx`)
3. 우대금리 상품 자격 판정(`RateProduct.requires_k_taxonomy_leads`)
4. (신규) 이 문서의 감축 실천 ToDo

즉 이번 수정은 감축 ToDo 하나가 아니라 **결선 시연에서 은행 리드·우대금리
화면도 함께 살아나는** 효과가 있다.

### 12.3 수정 — `db/scenarios.py`에 공통 설비 신호 전표 추가

`synth_generator.py` 본체(연료 단위 순회 구조)를 고치는 대신, 모든 시나리오가
공통으로 거치는 `db/scenarios.py::load_scenario()`에 설비 신호 전표 2건을
추가로 얹었다:
- **R031 매칭**("고효율 압축기") — `finance_lead_type` 있음 → 은행 리드·
  사장님 카드·우대금리 자격까지 전부 채움(실측 확인).
- **R058 매칭**("공조설비 유지보수비") — `finance_lead_type` 없음(원래도
  그런 룰)이지만, 감축 ToDo의 노후설비 의심 신호(`evidence LIKE
  '%(참고: R058)%'`)를 채움.

결손·이상치는 시나리오마다 달라야 하는 게 설계 의도지만, 설비 신호는 "부가
정보"라 어느 시나리오에 섞여 있어도 그 시나리오 고유 현상을 가리지 않는다는

성서테크 화면 확인 후 나온 두 가지 요청:

1. **"이렇게 하면 도움이 돼요"(goals 배경 섹션) 제거** — "이 내용은 필요

2. **목표 설정 시트에 "이번 달에 뭘 하면 감축되는지" 추가** — "목표

   문구("다음 측정 때 실제로 줄었는지...") 위에 "이번 달엔 이런 걸
   해보세요" 섹션을 추가했다. `ReductionTodoCard`와 같은 아이콘(체크)·톤을
   재사용해 두 화면의 시각 언어를 통일했다.

**한 가지 미결 사항**: 사용자가 그 전에 지적한 "todos가 주마다 안 바뀐다"(§14

변경 없음(순수 프론트 작업 + 기존 엔드포인트 재사용).

## 14. 열린 질문 — "이번주 할 일"인데 매주 안 바뀐다

사용자 확인 질문: "근데 이게 주마다 다른거임?". 답: 아니다. `todos`는 "이
기업에 이 설비 신호(K택소노미 매칭·R058)가 존재하는가"라는 **정적 판단**이라
신호가 그대로면 문장도 그대로다. "이번주"라는 이름과 실제 동작(시간 개념
없음)이 어긋난다.

검토했던 방향(아직 미확정, 다음 세션 과제):
- 후보가 여럿일 때 매주 하나씩 로테이션
- 최근에 새로 생긴 신호를 우선 노출, 이미 여러 번 보여준 건 우선순위 하향
- "이번주"라는 표현 자체를 시간 무관 톤("지금 확인해보세요")으로 낮추기

이 문서 갱신 시점까지는 방향 미결정 — §13의 두 요청(goals 제거, GoalSheet
연동)을 먼저 처리하느라 순서가 뒤로 밀렸다.

## 15. 안전한 카탈로그 재설계 + LLM 선별 도입 (2026-08-26)

### 15.1 배경 — 사용자가 직접 위험 사례를 제시

§11까지의 카탈로그는 "지게차 충전 시간을 야간으로 옮겨보세요"처럼 방법을
코드가 즉석에서 짧게 지어낸 문장이었다. 사용자가 두 가지 대안 문구를 직접
제시하며 방향을 물었다:

- "콤프레샤 토출 압력을 0.5~1bar 정도 낮춰 전력 낭비를 막아보세요" — 숫자가
  들어간 정비 지시
- "한전 파워플래너로 피크 시간대를 확인하고 고부하 설비 가동을 분산해보세요"
  — 외부 도구로 위임하는 방식

실제 근거를 웹서치로 검증한 결과, 사용자가 예시로 든 "0.5~1bar" 수치는
한국에너지공단 공식 권고("0.1bar씩 점진적으로")와 5배 어긋났다 — 직관적으로
그럴듯한 수치도 사람이 확인하지 않으면 틀릴 수 있다는 실증 사례. 이걸 근거로
안전 기준 3단계를 확정했다(코드 주석 `db/pcaf_engine/reduction_todo.py` 상단
"안전한 카탈로그" 섹션 참고):

1. **1순위 — 외부 공인 도구/기관 위임.** 숫자 자체가 없어 가장 안전(한전
   파워플래너 안내).
2. **2순위 — 검증된 정비 스펙.** 사람이 공신력 있는 출처로 사전 검증하고
   코드에 고정. LLM이 즉석 생성 금지.
3. **3순위 — 근거 없으면 문구 자체를 안 넣는다.**

### 15.2 절약 예상값 전면 배제

사용자 확정 지시: "절약 예상값 보여줄 생각 없음 + 환각이 생길 수 있는 제안이나
계산은 금지." 카탈로그 전체를 재점검해 두 곳에서 절약 예상값을 제거했다:

- `_COMPRESSOR_TODO_NOTE`: "압력 1kg/㎠ 하향 시 축동력 6~8% 감소" 수치 제거,
  "왜 0.1bar씩인가"(급격한 하향 시 공정 지장)만 남김.
- `FALLBACK_TIPS`(`db/pcaf_engine/reduction_actions.py`): "연간 약
  110kgCO2e·34,000원", "연간 약 17kgCO2e" 수치 제거. 이 수치는 애초에 스스로
  "가정 기준 참고치"라고 표기했던 것으로, 사업장 대상 카드에 적용 근거가 없어
  원칙10(확정치처럼 표기 금지)에도 걸리는 이중 문제였다 — 단순 표기 순화가
  아니라 애초에 이 카드에 들어오면 안 됐던 값을 뺀 것.

note가 사라진 항목은 `None`으로 남긴다(빈 문자열이 아니라 "이 항목엔 부가
설명이 없다"는 걸 명시적으로 표현).

### 15.3 LLM 선별 — "문구는 그대로, 순서만"

사용자 2차 요청: "기업의 배출량(연료별)·규모·업종·동종업계 데이터를 LLM에게
주면 그에 맞춰 투두 설계." AskUserQuestion으로 범위를 두 단계 좁혔다:

- 1차 확인: "새 문장을 LLM이 짓는가, 아니면 정적 카탈로그 중 선별만
  하는가" → **"선별만 LLM, 문구는 여전히 정적 카탈로그"** 확정.
- 2차 확인: "카탈로그를 확장해서라도 다양한 후보를 주고 고르게 할지, 이미
  매칭된 것만 순서를 바꿀지" → **"이미 매칭된 것만 순서 재배치"** 확정.

구현(`_llm_rerank_todos`, `db/pcaf_engine/reduction_todo.py`):

- **입력**: `goals`(3층 결과 — 연료별 기준월↔최근월 tCO2e, 이미 계산되어
  있음, 새 계산 없음), 업종·규모(`Company.industry_name`/`employee_count`),
  동종업계 중앙값(`api/queries.py::get_distribution()`, 1층을 LLM 컨텍스트로
  재사용 — 액션을 1층으로 직접 필터링하지 않는다는 기존 원칙과는 다른 결,
  "배경 정보로 주는 것"과 "그 값으로 직접 걸러내는 것"은 별개 판단이라는
  합의).
- **출력**: candidate id 문자열만 쉼표로 나열. 숫자·문장 필드가 스키마에
  아예 없어 원칙1(LLM 산수 금지)과 동일한 방어 구조 — `db/document_llm_router.py`
  (셀 id만 고르고 값은 정규식이 재파싱)와 같은 결.
- **검증**: 후보에 없는 id, 중복, 누락은 전부 무시하고 원래 순서로 뒤에
  보정한다(`ordered += [t for t in todos if t["id"] not in seen_ids]`) — 반환
  집합이 항상 원래 후보 id 전체와 정확히 일치하도록 강제.
- **실패 처리**: 키 없음·호출 실패·응답 파싱 실패는 전부 조용히 원래 순서로
  폴백한다. `_judge_anomaly_with_llm`(이상치 판단)과 달리 실패를 트레이스에
  남기지 않는다 — 이 판단은 "계산"이 아니라 "정렬 취향"이라 실패해도 사장님이
  검토해야 할 이상 상태가 아니라는 게 이유(코드가 이미 정한 순서 자체가
  유효한 결과).
- **적용 범위**: `_facility_todos()`(설비 신호 매칭분)만 대상. `FALLBACK_TIPS`
  경로는 제외 — 개인화할 기업 맥락(연료별 변화·설비 신호)이 애초에 빈약해
  순서를 바꿀 근거가 없다.

### 15.4 부수 수정 — `_facility_todos`의 폴백 판단 버그

이번 작업 중 발견한 사전 존재 버그: 공기압축기 팁이 "설비 신호 유무와 무관하게
항상 포함"되도록 바뀌면서(§15.1), `_facility_todos(signals) or _tip_todos()`의
`or` 분기가 무력화됐다 — 설비 신호가 0개인 기업도 압축기 팁 1개 때문에
`_facility_todos()`가 빈 리스트를 반환하지 않아, 폴백(§6, 빈 화면 금지 취지의
최소 3개 채움)이 걸리지 않고 todos가 1개만 나오는 회귀가 있었다(테스트 2건
실측 확인). `_has_k_taxonomy_signal()`을 추가해 "K택소노미 매칭 신호(설비
유형·노후설비 의심)가 있는가"와 "압축기 팁 포함 여부"를 분리해 수정했다.
