## 1. 착수 조건

data-plan.md §15.1(회계 1순위)이 끝나야 정확한 스펙으로 시작할 수 있다. 특히:

- 사업자참여신청서(hwp) 실물 없이는 `db/carbon_neutral_point.py`의 신청서 초안 생성 함수를
  정확한 필드로 못 만든다 — 추정 필드로 먼저 골격만 잡고, 실물 확인되면 필드를 맞추는 순서로
  진행 가능(완전히 막히는 건 아님)
- 감축률 산정 공식의 세부 방식(회계 전화 확인 대기 중)이 안 나오면 계산 함수의 정확도를
  보장 못 한다 — 이건 골격만 먼저 짜고 공식만 나중에 끼워 넣는 식으로 병행 가능

즉 "완전히 대기"는 아니고, 골격은 지금 시작하되 정확한 필드·공식은 회계 결과를 기다린다.

## 2. 개발자 A (백엔드)

### 2.1 소상공인 자동 판별

- **`business_scale_hint` 계산 함수 추가 — 저장하지 않는다.** data-plan.md §5·§6.1이
  명시한 대로, `Company` 또는 신규 테이블에 `business_type` 같은 저장형 컬럼을 만들지
  않는다. 대신 조회 시점에 그 기업의 최근 `electric_bill` 문서(`source_documents`)에서
  `contract_type_class`(§7.1)를 읽어 `"제조업/산업체" | "소상공인/상업시설" | "미확인"`을
  **매 요청마다 계산**하는 순수 함수로 만든다. 이렇게 해야 사업장이 계약종별을 바꿔도
  마이그레이션 없이 자동으로 갱신된다 — 저장형으로 만들면 이 이점이 사라진다
- 전기고지서 파싱 단계(`db/document_extraction.py` 계열)에 계약종별 추출 로직 추가
  (data-plan.md §7.1, §11)

### 2.2 감축률 계산

- 감축률 계산 함수 — 기존 이상치 자가검증 엔진(`_check_anomalies`, 평월 중앙값 대비 배수
  계산)과 같은 결의 순수 파이썬 함수로, 회계가 확정한 산정공식대로 계산 + 5% 임계값 체크
- **반환값은 반드시 "예상치"로 취급한다.** data-plan.md §6.2가 명시한 대로, 이 계산은
  감탄의 자체 추정치이지 공식 판정이 아니다 — 공식 판정은 한국환경공단이 한전 등으로부터
  직접 받은 데이터로 반기(6월·12월)마다 자체 계산한다. 함수 반환 필드명도
  `estimated_reduction_rate_pct`로 하거나 응답에 `is_estimate: true`를 반드시 포함한다
  (data-plan.md §14-8, 아직 미확정 — 프론트와 합의 후 확정)

### 2.3 알림·신청서

- 임계값 충족 시 알림 트리거 — 기존 "등급 상승 후보 판정" 패턴(PR #40, #43-47) 그대로
  재사용, `business_scale_hint == "소상공인/상업시설"`일 때만 활성화(저장값이 아니라
  §2.1의 계산값 기준으로 분기)
- 신청서 초안 생성 함수 — 회계의 필드 매핑표(data-plan.md §15.2) 기준으로 기존 계산값을
  텍스트/PDF 초안에 채워 넣기. LLM 산수 없음, 값 그대로 대입(원칙1)
- 신청서 초안·알림 문구 어디에도 감축률을 확정치처럼 표기하지 않는다 — §2.2의 예상치
  라벨링을 신청서 초안 자체에도 동일하게 적용(예: "예상 감축률" 문구로 통일)

### 2.4 온보딩 리워드

- 마이데이터 연동 완료 시 `trace_logs`에 `[행동] 온보딩 리워드 지급 안내` 기록하는 이벤트
  훅. **실제 송금 아님** — 데모용 로그 + 안내 문구만
- 이 항목은 회계 1순위(온보딩 리워드 예산 확인, data-plan.md §15.1)가 끝나기 전까지는
  로그 문구를 확정적으로 쓰지 않는다("지급 안내"까지는 괜찮지만 금액을 못박지 않는 식)

### 2.5 이번 스프린트에서 하지 않는 것

- 그린 서플라이어 배지용 API — data-plan.md §3.4·§12에 따라 Tier3로 재분류됐다. "신규
  로직 없음(기존 PCAF 등급 재사용)"이라 가벼워 보여도, 이번 스프린트에 끼워 넣지 않는다.
  Tier1·2가 다 끝난 뒤 팀이 다시 논의해서 착수 여부를 정한다

## 3. 개발자 B (프론트엔드)

개발자 A의 API가 나오는 대로 순차 진행하되, UI 시안은 먼저 시작할 수 있다.

### 3.1 온보딩 리워드 배너

- 마이데이터 연동 완료 화면에 리워드 안내 배너
- **문구는 회계 1순위(온보딩 리워드 예산 확인)가 끝나기 전까지 확정적으로 쓰지 않는다.**
  "대구로페이 1만원 충전 예정"처럼 금액·시점을 못박은 문구 대신, 확인 전에는 "온보딩 혜택
  안내(검토 중)"처럼 잠정 톤으로 시작하고 확인되면 문구만 교체한다(data-plan.md §3.3 안전한
  표현 원칙)

### 3.2 사장님 화면 분기

- 화면 분기는 저장된 `business_type` 컬럼이 아니라 §2.1의 API 응답값(`business_scale_hint`)
  기준으로 한다 — 제조업 카드(K택소노미·우대금리 등 기존 카드)와 소상공인 카드(탄소중립포인트
  알림)를 이 값으로 나눈다

### 3.3 탄소중립포인트 알림·신청서 화면

- 신청 가능 알림 + 신청서 초안 미리보기/다운로드 화면
- **비보장 문구 필수**: "예상 감축률 기준이며, 실제 심사·지급은 한국환경공단이 진행합니다"
  같은 문구를 화면에 명시(§2.3과 대응, data-plan.md §6.2·§3.3 근거)

### 3.4 트레이스 뷰

- 신규 이벤트 타입 반영 — `[행동] 온보딩 리워드 지급 안내`, `[행동] 신청서 초안 생성` 등
  아이콘·색 추가

### 3.5 이번 스프린트에서 하지 않는 것

- 그린 서플라이어 배지 UI(iM샵 프로필 목업 포함) — 2.5와 같은 이유로 Tier3, 이번
  스프린트 제외
