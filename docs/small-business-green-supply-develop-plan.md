## 1. 착수 조건

data-plan.md §15.1(회계 1순위)이 끝나야 정확한 스펙으로 시작할 수 있다. 특히:

- 사업자참여신청서(hwp) 실물 없이는 `db/carbon_neutral_point.py`의 신청서 초안 생성 함수를
  정확한 필드로 못 만든다 — 추정 필드로 먼저 골격만 잡고, 실물 확인되면 필드를 맞추는 순서로
  진행 가능(완전히 막히는 건 아님)
- 감축률 산정 공식의 세부 방식(회계 전화 확인 대기 중)이 안 나오면 계산 함수의 정확도를
  보장 못 한다 — 이건 골격만 먼저 짜고 공식만 나중에 끼워 넣는 식으로 병행 가능

즉 "완전히 대기"는 아니고, 골격은 지금 시작하되 정확한 필드·공식은 회계 결과를 기다린다.

## 2. 개발자 A (백엔드)

### 2.1 소상공인 자동 판별

- **`business_scale_hint` 계산 함수 추가 — 저장하지 않는다.** data-plan.md §5·§6.1이
  명시한 대로, `Company` 또는 신규 테이블에 `business_type` 같은 저장형 컬럼을 만들지
  않는다. 대신 조회 시점에 그 기업의 최근 `electric_bill` 문서(`source_documents`)에서
  `contract_type_class`(§7.1)를 읽어 `"제조업/산업체" | "소상공인/상업시설" | "미확인"`을
  **매 요청마다 계산**하는 순수 함수로 만든다. 이렇게 해야 사업장이 계약종별을 바꿔도
  마이그레이션 없이 자동으로 갱신된다 — 저장형으로 만들면 이 이점이 사라진다
- 전기고지서 파싱 단계(`db/document_extraction.py` 계열)에 계약종별 추출 로직 추가
  (data-plan.md §7.1, §11)
- **같은 작업에 고객번호 추출도 함께 넣는다(2026-08-22 추가).** PR #112로 확정된 실제 신청서
  서식에 고지서 고객번호가 전기·수도·도시가스·지역난방 4종으로 들어 있다(data-plan.md §6.3).
  §6.3이 전기 고객번호를 "기존" 데이터로 적어놨었는데 **사실이 아니다** — 현재 전기고지서
  파서는 고객번호를 추출하지 않는다(코드 확인 후 §6.3 정정함). 계약종별과 같은 정규식 파서를
  건드리는 작업이라 따로 진행하지 않고 한 번에 넣는다. 도시가스·지역난방 고객번호는 이번
  범위 밖(data-plan.md §3.2)이라 신청서 초안에서 잔여 필드로 남는다

### 2.2 감축률 계산

- **전제: 최소 24개월(과거 2년)치 사용량 데이터가 필요하다.** 원본 브레인스토밍 근거 —
  대구시 탄소중립포인트 감축률 산정 자체가 "과거 2년치 사용량 평균 대비 금년 사용량"
  기준이다. 감탄 코어 파이프라인은 기본이 "12개월치 전표"(CLAUDE.md §7)라서, 기존
  `get_vouchers()`·`Classification` 조회 계열 함수가 12개월을 암묵 전제로 짜여 있는지
  먼저 점검하고 24개월 조회로 확장 가능한지 확인해야 한다. S001·S002 fixture가 이미
  2024-01~2026-08 32개월치로 이 요구사항을 반영해뒀다(`data/fixtures/electricity_bills/
  S001`, `S002`)
- **신규 가입자 예외**: 과거 2년치 데이터가 없는(마이데이터 연동 이력 2년 미만) 신규 가입
  기업은 24개월 평균 대신 **1년치 평균으로 대체**한다 — 원문 명시 규칙. 계산 함수 분기에
  반드시 포함(누락 시 신규 온보딩 기업은 전부 계산 불가 상태가 됨)
- 감축률 계산 함수 — 기존 이상치 자가검증 엔진(`_check_anomalies`, 평월 중앙값 대비 배수
  계산)과 같은 결의 순수 파이썬 함수로, 회계가 확정한 산정공식대로 계산 + 5% 임계값 체크
- **정산 주기(반기) 헬퍼**: 원문 — "가입월 다음 달부터 6개월 단위로 정산(6월·12월 지급)".
  `carbon_neutral_point_enrollments.enrolled_at` 기준으로 다음 정산월을 계산하는 함수
  필요 — §2.3 알림·신청서에서 "언제 지급되는지" 안내할 때 사용
- **수도(water) 데이터는 스키마만 먼저 준비한다.** 원문은 전기·수도·도시가스 3종 모두
  포인트 지급 대상으로 명시한다. `water_bills` 테이블(data-plan.md §7.2)과
  문서종류 어휘의 `water_bill`은 이번에 추가하되(**후자는 DDL이 아니다** —
  `document_type`이 DB enum이 아니라 `String(50)`이라 코드 레벨 목록만 고치면 된다,
  2026-08-22 확인·data-plan.md §7.2 참고), 실 서식(§14-2) 미확보 상태라
  파싱 로직은 없이 컬럼만 만든다 — 전기만으로 계산하면 실제보다 감축률·포인트가
  부정확해진다는 점을 사장님 화면에 명시적으로 고지한다("수도·가스 사용량은 아직
  반영되지 않아 실제와 차이가 있을 수 있어요")
- **반환값은 반드시 "예상치"로 취급한다.** data-plan.md §6.2가 명시한 대로, 이 계산은
  감탄의 자체 추정치이지 공식 판정이 아니다 — 공식 판정은 한국환경공단이 한전 등으로부터
  직접 받은 데이터로 반기(6월·12월)마다 자체 계산한다
- **필드명은 그대로 `reduction_rate_pct`, 플래그 추가 없음(2026-08-21 확정, data-plan.md
  §14-8·§6.2).** 이 엔드포인트는 항상 예상치만 반환하므로 `is_estimate` 같은 플래그는 항상
  `true`라 정보량이 없다. "예상치" 표기는 백엔드가 아니라 프론트 쪽 책임(§3.3)이다 — 계산
  함수·API 응답 스키마는 변경 사항 없음

### 2.3 알림·신청서 — **구현 완료(2026-08-24)**

`db/carbon_neutral_point.py`에 `evaluate_eligibility()` / `notify_if_eligible()` /
`build_application_draft()` 3종으로 구현. 테스트 16건.

- **알림 트리거** — 자격 충족 시에만 `OwnerNotification`을 만든다. "등급 상승 후보 판정"
  패턴(`db/pcaf_engine/rate_approvals.py::create_rate_request`)에서 가져온 것은 **근거 없이는
  레코드를 만들지 않는다**는 규칙이다(거기서 활동자료 없으면 예외로 거부하는 것과 같은 이유로,
  여기서는 자격 미충족·계산 불가면 None 반환).
- **중복 방지는 이 테이블의 첫 사례였다** — `owner_notifications`엔 유니크 제약도 기존 dedup
  코드도 없다(기존 3종 `classification_sent`·`document_processed`·`document_failed`는 잡·전송
  액션당 1건이라 문제가 없었다). 감축률은 조회마다 판정이 도니 가드가 필요해, 같은 기업·같은
  타입의 **안 읽은** 알림이 있으면 새로 만들지 않는다. **한계를 알고 쓴다**: 동시 요청 레이스는
  못 막는다(`source_documents`가 `(company_id, file_hash)` 유니크로 최종 방어선을 둔 것과 대조).
  폴링 배너라 최악이 "알림 2개"여서 마이그레이션까지 하지 않았다 — 문제가 되면
  `(company_id, type, 정산구간키)` 유니크 인덱스를 새 revision으로 추가한다.
- **비보장 문구는 알림·API에 담지 않는다** — data-plan.md §6.2가 "예상치" 표기를 프론트 정적
  문구로 강제하기로 확정했고 `CarbonPointCard`가 이미 렌더한다. 대신 알림 message 자체를
  "예상 감축률"로 쓰고 "확정"이라는 단어가 들어가지 않는지 테스트로 잠갔다.
- **제조업은 감축률도 사용량도 계산하지 않는다** — 처음엔 감축률만 null이고 사용량은 채워
  보냈는데, "계산은 했는데 결과만 감췄다"처럼 보여 §6.2 원천 제외 취지와 어긋났다(실 DB 확인
  중 발견해 수정).
- **신청서 초안** — 프론트 `CarbonPointDraft` 계약대로 `fields[{label, value, source}]` 14개 +
  `remaining_fields` 9개 반환. 라벨 문구까지 백엔드가 정한다(프론트는 배열을 그대로 렌더).
  자격 충족 시에만 `carbon_neutral_point_applications` 레코드를 남긴다(미달 기업 신청서를 DB에
  쌓지 않는다). 수치는 `compute_reduction_rate()` 결과를 그대로 대입 — LLM 개입 없음(원칙1).
  못 채운 값은 빈 문자열이 아니라 `None`(실패 가시성).
- 서식에 남은 가정용 항목(거주 면적·세대원 수·전입일자)은 공란으로 두고 **잔여 필드로도 넣지
  않는다** — 사장님에게 "채우세요"라고 안내할 근거가 없다(data-plan.md §6.3 지적).

#### data-plan.md §6.3 출처 오기재 정정 (2026-08-24)

§6.3이 "마이데이터 사업자등록증명 (기존)"으로 적어둔 항목 중 실제로 그 페이로드에 없던 것들.
성격이 달라 다르게 처리했다.

- **사업장 주소 → mock에 추가했다.** 실제 사업자등록증명원에는 인쇄돼 나오는 항목인데 우리
  mock 범위에서만 빠져 있었다(회계 합성데이터 가이드의 `key_fields`가 "사업자번호, 기업명"으로
  좁게 잡힌 데서 비롯). `api/mydata_kyb_mock.py::_synthetic_business_registration`에
  `site_addr`를 추가했다. 세부 주소는 `Company.region` + mock임이 드러나는 형태로 만든다 —
  실제 지번을 지어내면 합성값을 진짜 주소처럼 보이게 만드는 셈이다(§3.3 과장 방지).
  우편번호는 사업자등록증명에 없으므로 넣지 않았다(잔여 필드).
- **휴대전화번호·전자메일 → 잔여 필드로 확정.** 마이데이터 5종은 국세청·중소벤처기업부·한전이
  주는 서류라 연락처가 없다. 실서비스라면 은행 내부 고객정보에서 와야 하는데 그건 마이데이터가
  아니고(`InstitutionBorrower`에 연락처 컬럼이 없는 이유) 연동 가능성도 우리가 결정할 수 없다 —
  mock으로 지어내면 "이미 가진 데이터"인 척하게 된다.
- 전기 고지서 고객번호도 같은 부류의 오기재였고 §2.1에서 신규 추출로 처리했다.

**공유 DB 반영 완료(2026-08-24)**: 마이데이터 mock이 멱등(이미 수집됐으면 기존 값 반환)이라
기존 `business_registration` 4건은 재수집으로 갱신되지 않았다 — 참조 0건을 확인하고 삭제 후 다시
수집했다(`vouchers`로 변환되지 않는 KYB 문서라 연결 데이터가 없다). 아직 마이데이터를 안 받았던
5개 기업도 함께 수집돼 9개 기업 전부 `site_addr`를 갖는다. 신청서 초안에서 14개 필드 중 8개가
자동으로 채워진다(상호·대표자·사업자등록번호·주소·전기 고객번호·기준/감축년도 사용량·예상 감축률).

### 2.4 온보딩 리워드 — **개발 제외 (2026-08-24 결정)**

원래 항목: "마이데이터 연동 완료 시 `trace_logs`에 `[행동] 온보딩 리워드 지급 안내` 기록하는
이벤트 훅(실제 송금 아님, 데모용 로그 + 안내 문구만)".

**이번 개발 범위에서 뺀다.** 리워드(대구로페이 충전 등)는 감탄이 계산·판정하는 대상이 아니라
예산·정산이 걸린 대외 협의 사항이고, 예산 확인 전에는 화면·로그 문구를 확정적으로 쓸 수 없어
"지급 안내(검토 중)" 수준의 잠정 표현만 남는다 — 그 상태로 만들면 나중에 문구를 다시 갈아야 하고,
데모에서도 "실제 송금이 아니다"라는 각주를 계속 달아야 한다.

파급 효과:

- **회계 작업이 하나 줄어든다** — data-plan.md §15.1의 "온보딩 리워드 예산 관련 은행 담당자·멘토
  문의"(원래 3순위였다가 개발자 B 화면 문구 때문에 1순위로 승격됐던 항목)가 더 이상 개발 선행
  조건이 아니다. 남은 회계 1순위는 감축률 산식 세부 확인 하나뿐이다.

### 2.7 API 엔드포인트 — **구현 완료(2026-08-24)**

data-plan.md §9.1 4종을 `api/routers/owner.py`에 추가했다(테스트 11건). 응답 필드명·타입을
프론트 `CarbonPointEligibility`·`CarbonPointDraft`와 맞췄다 — fixture를 이 API로 교체할 때
컴포넌트를 안 고치는 것이 목적이다.

```text
GET   /owner/{id}/carbon-point/eligibility        6필드. target_year 생략 시 올해
POST  /owner/{id}/carbon-point/applications       fields[] 14개 + remaining_fields 9개
GET   /owner/{id}/carbon-point/applications/{id}  단건 조회
PATCH /owner/{id}/carbon-point/applications/{id}  제출 이후 상태를 사장님이 직접 갱신
```

설계 결정 3개:

- **판정 구간을 쿼리 파라미터로 받는다**(`target_year`·`target_start_month`·`months`). 정산
  구간이 6개월이라는 건 확정이지만 시작점이 미확정이라(§2.2) 서버가 임의로 정하지 않고 기본값만
  둔다 — 확정되면 기본값을 바꾸면 된다.
- **자격 미달 기업도 초안 미리보기는 받지만 `application_id`가 null이다** — 신청 대상이 아닌
  기업의 신청서를 DB에 쌓지 않는다(rate-requests가 근거 없는 요청을 거부하는 것과 같은 결).
- **PATCH는 `draft`로 되돌리기를 422로 막는다** — 이미 제출한 사실을 지우는 셈이라 이력이
  왜곡된다. 남의 초안 조회·수정은 404(테넌트 경계, 기존 goal·documents 패턴).

실 DB 확인: 동성로카페 6.8% 자격 있음 / 반월당분식 -2.33% 미달 / 대경부품 제조업 null,
초안 14필드 중 8개 자동 채움, 남의 초안 접근 404.

시나리오 토글은 URL 쿼리 `?cp=`로 한다. 쿼리 파싱은 `useSyncExternalStore`로 한다 —
`useCarbonPointScenario()` 훅이 `popstate`를 구독하고 서버 스냅숏으로 기본 시나리오를 준다.
후보 두 개를 다 버린 이유가 있다.

- `useSearchParams()`: 정적 프리렌더 라우트에서 Suspense 경계를 요구해 기존 페이지 구조를
  건드려야 한다
- `useEffect` + `setState`: 이 프로젝트 lint가 `react-hooks/set-state-in-effect`를 **error**로
  잡는다(React 19 규칙, 기존 파일 13건이 이미 걸려 있어 신규 코드로 늘리지 않는다)

`useSyncExternalStore`는 브라우저의 외부 상태를 읽는 정석 훅이라 하이드레이션 불일치 경고도
없다. 예외가 한 곳 있다: `benefits/page.tsx`의 조회 게이팅 effect는 훅 값 대신
`resolveScenario(window.location.search)`를 직접 읽는다 — 그 effect는 하이드레이션 직후에도 도는데
그 시점 훅 값은 서버 스냅숏(기본 시나리오)일 수 있어서다.

```text
?cp=manufacturing            제조업/산업체 (기본값 — 쿼리 없이 들어오면 이것, 기존 화면 무변화)
?cp=commercial_eligible      소상공인/상업시설 + 자격 충족
?cp=commercial_not_eligible  소상공인/상업시설 + 감축률 미달
?cp=unknown                  미확인(계약종별 판별 실패)
```

fixture가 활성인 동안 카드에 `예시 데이터 · API 연동 전` 칩을 상시 노출한다 — 데모에서 실제

### 3.2 사장님 화면 분기

- 화면 분기는 저장된 `business_type` 컬럼이 아니라 §2.1의 API 응답값(`business_scale_hint`)
  기준으로 한다 — 제조업 카드(K택소노미·우대금리 등 기존 카드)와 소상공인 카드(탄소중립포인트
  알림)를 이 값으로 나눈다
- **분기 규칙 확정(2026-08-21)** — 대상 화면은 `web/app/owner/benefits/page.tsx`:

```text
"소상공인/상업시설" → RateProductCard·KTaxonomyCard·GovSupportCard 미렌더 + 그 3종 API 조회도
                     건너뜀, CarbonPointCard만 노출
"제조업/산업체"     → 현행 그대로, CarbonPointCard 숨김(data-plan.md §10.1 — 산업용 전기는
                     탄소중립포인트 에너지분야 원천 제외라 카드 자체를 안 보여준다)
"미확인"           → 현행 3카드 유지 + 상단에 계약종별 확인 안내 박스
                     (/owner/uploads?type=electric_bill 딥링크, 기존 딥링크 규약 재사용)
```

- `"미확인"`에서 기존 카드를 **숨기지 않는** 이유: data-plan.md §6.1이 이 경우를 "계약종별 재확인
  요청(HITL)"으로 규정했다. 판별에 실패한 상태에서 이미 받던 안내를 없애는 건 잘못 숨기는 쪽의
  손해가 더 크다 — 안내를 추가하는 방향으로만 처리한다
- 지금은 fixture가 동기값이지만, API 전환 시 자연스럽게 2단 로딩(hint 먼저 → 카드 조회)이 되도록
  "hint 확정 전에는 카드 영역을 렌더하지 않는" 구조로 미리 작성한다

### 3.3 탄소중립포인트 알림·신청서 화면

- 신청 가능 알림 + 신청서 초안 미리보기/다운로드 화면
- **컴포넌트명은 `CarbonPointCard`로 확정.** data-plan.md §10.1은 이 카드를 `GovSupportCard`로
  적었는데, 그 이름은 이미 `web/components/GovSupportCard.tsx`(정부 지원사업 매칭 카드,
  gov-support-matching-plan.md §8)가 점유하고 있어 충돌한다 — 설계문서가 우선이라는 원칙의
  예외로, 이 항목만 이 문서의 이름을 따른다
- **배치 확정**: 홈(`/owner`)에는 알림 배너(`CarbonPointNoticeBanner`), 혜택
  페이지(`/owner/benefits`)에는 자격 요약 카드 + 초안 시트. 배너는 `eligible`이 아니거나
  소상공인이 아니면 렌더하지 않고, 누르면 혜택 페이지로 보낸다
- **초안 화면은 바텀시트**(`CarbonPointDraftSheet`) — 기존 `GoalSheet.tsx`의 셸
  (`fixed inset-0 z-50 flex items-end` + `rounded-t-3xl bg-surface`, 배경 클릭 닫기)을 그대로
  재사용한다. 하단바 4탭에 안 들어가는 고아 라우트를 새로 만들지 않기 위해서다
- **다운로드 버튼은 비활성 + "초안 생성 기능 준비 중"** 표기. 초안 생성 함수(§2.3)가 아직
  없으므로 가짜 파일을 내려주지 않는다(CLAUDE.md §6 실패 가시성)
- "신청서 초안 보기" 버튼은 `eligible`일 때만 노출한다(data-plan.md §6.2 — 판정을 통과한 경우에만
  신청 절차로 이어진다). 미달이면 버튼 대신 "예상 감축률이 5%를 넘으면 초안을 만들어 드려요"로
  왜 아직 안 되는지만 알린다
- 자격 미달(`eligible: false`)이어도 카드 자체는 보여준다 — "기준 미달" 배지와 현재 예상 감축률을
  같이 노출해야 사장님이 얼마나 남았는지 알 수 있다. 카드를 숨기는 기준은 자격이 아니라
  `business_scale_hint`다(§3.2)
- 실물 hwp 서식이 미확인이라(data-plan.md §14-1) 초안 필드는 fixture의 배열을 그대로 렌더하는
  구조로 둔다 — 서식이 확인되면 fixture만 고쳐도 화면이 따라온다
- 신청서 초안 화면 어디에도 감축률을 확정치처럼 표기하지 않는다 — "예상 감축률"로 통일(§2.3 대응)
- **비보장 문구 필수, 구현 방식 확정(2026-08-21)**: API에 플래그가 없으므로(§2.2) 이 문구는
  `CarbonPointCard` 컴포넌트에 정적 텍스트로 박아넣는다. `GoalSheet.tsx`(§209 근처)의
  "등급·혜택 목표는 데이터 완전성 개선을 제안할 뿐 등급 상승·자격을 보장하지 않아요"와 같은
  스타일(`text-[11px] leading-relaxed text-faint`)로 "예상 감축률 기준이며, 실제 심사·지급은
  한국환경공단이 진행합니다" 문구를 고정 렌더링한다(§2.3과 대응, data-plan.md §6.2·§3.3 근거)

### 3.4 트레이스 뷰 — 이번 스코프 제외 (2026-08-21 정정)

원래 항목: "신규 이벤트 타입 반영 — `[행동] 온보딩 리워드 지급 안내`, `[행동] 신청서 초안 생성`
등 아이콘·색 추가".

**코드를 확인한 결과 추가할 자리가 없다.** `web/components/SceneTrace.tsx`의 `STEP_ICON`은
`계획`/`관찰`/`행동` 3종 `step_type`에만 매핑되고(`trace_logs`의 스키마가 그렇다 — CLAUDE.md §4-6,
"결선까지 불변"), 도구명은 `tool_name` 뱃지로 이미 자동 렌더링된다. 위 두 이벤트는 **둘 다 기존
`행동` 타입**이라 개발자 A가 `trace_logs`에 쓰기만 하면 프론트 수정 없이 그대로 표시된다.

도구별로 아이콘을 다르게 주고 싶다면 `tool_name` 기준 새 매핑을 만드는 별개 작업이 되는데, 그건
원래 계획과 다른 일이라 이번 스프린트에서 하지 않는다.

### 3.5 이번 스프린트에서 하지 않는 것

- 그린 서플라이어 배지 UI(iM샵 프로필 목업 포함) — 2.5와 같은 이유로 Tier3, 이번
  스프린트 제외
- **온보딩 리워드 배너 — §3.1 참고(2026-08-24 개발 제외).** 이미 병합된 컴포넌트의 유지·제거는
  개발자 B와 협의 필요
- §3.4 트레이스 뷰 아이콘·색 추가 — 위 정정 참고(할 일이 없음)
- **실제 API fetch 연동** — fixture로 껍데기까지만. 연동은 §9.1 엔드포인트가 나온 뒤 별도 작업
- **`water_bill` 문서종류 프론트 확장** — 감축률은 전기+수도+가스 기준인데(data-plan.md §7.3)
  개발자 A 작업목록(§2)에 상수도 고지서 파싱이 아예 없다. 프론트 쪽도 `SceneUpload.tsx`의
  `DocType`·`DOC_LABELS`·`RequiredDocuments`, `uploads/page.tsx`의 `DOC_LABEL`,
  `admin/DocumentAccessLog.tsx`, `lib/api.ts`의 `DocumentType`이 전부 3종 하드코딩이라 4곳 이상을
  고쳐야 하는데, 백엔드 파싱이 없으면 업로드 칸만 붕 뜬다 — 개발자 A와 합의 후 별도 착수
- 신청서 초안 실제 생성·다운로드 — §2.3이 나온 뒤

### 3.6 검증 방법

프론트에 테스트 프레임워크가 없다(`web/package.json`에 `dev`/`build`/`start`/`lint`만, `*.test.tsx`
0건). 이번 스코프를 위해 새로 도입하지 않고 아래로 검증한다.

- `npm run build` — Next 빌드에 타입체크가 포함된다. **기준선: EXIT=0**(2026-08-21 실측)
- `npm run lint` — **기준선이 이미 red다**: 24 problems(13 errors, 11 warnings)이 이번 작업 전부터
  있었고 전부 기존 파일의 `react-hooks/set-state-in-effect`·`refs`·`exhaustive-deps`
  ·`no-unused-vars`다. 그래서 판정 기준은 "0건"이 아니라 **"이 숫자가 늘지 않았고 신규 파일이
  목록에 없다"**다. 이번 작업 후에도 24 problems 그대로 확인함
- fixture 시나리오 4종 × 화면(홈·혜택·초안 시트) 수동 매트릭스 확인
- **회귀 기준**: `?cp=` 없이 들어온 화면이 이번 작업 전과 동일해야 한다(기본값이 `manufacturing`인
  이유)
