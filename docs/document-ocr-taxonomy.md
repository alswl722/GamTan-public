# 문서 인식 분류 체계 (OCR 입력 시나리오 taxonomy)

> 이 문서는 "어떤 종류의 업로드 파일이 들어올 수 있고, 각각 지금 어떤 경로로 처리되며,
> 어디까지 실제로 검증됐는지"를 한눈에 보기 위한 참고표다. CLAUDE.md §7이 아키텍처
> 원칙(단일 기준 문서)이라면, 이 문서는 그 아래 실제 시나리오별 커버리지 지도다.
> 새 문서 유형·입력 형식을 추가할 때마다 이 표에 행을 추가한다.

## 왜 이 표가 필요한가 — KB·로민 사례 대비 우리 위치

국내 은행권 자체 OCR(KB국민은행 KB AI-OCR, 하나은행 리딧, 로민 Textscope 등)은 전부
**학습된 문서분류 모델**을 1단계로 둔다 — 문서 종류가 다양해질수록 규칙을 손으로
늘리는 대신, 라벨링된 데이터로 분류기를 학습시켜 대응한다. 로민 Textscope는 "실환경
문자인식(Scene Text Recognition)"을 핵심 기술로 내세우며 저조도·흔들림·팩스 노이즈·
회전 각도에 강함을 별도로 검증한다.

감탄은 2026-08-15 결정에 따라 **ML 분류 모델도, LLM도 없이 정규식 키워드 매칭**으로
간다(공모전 방어 논리 — "환각이 개입할 경로 자체가 없다"를 OCR 단계까지 확장, §CLAUDE.md
§7). 이건 의도된 트레이드오프지 실수가 아니다: 대신 이 표로 "규칙이 실제로 아는 범위가
어디까지인지"를 명시적으로 관리해 방어 논리를 뒷받침한다.

이 트레이드오프의 실제 대가는 은행권 표준과 비교했을 때 명확하다:

| | KB/로민(ML 분류기) | 감탄(규칙 기반) |
| --- | --- | --- |
| 새 서식 대응 | 라벨링 데이터로 재학습 | 사람이 정규식·키워드 추가 |
| 처음 보는 문구 | 학습 분포 안이면 일반화 가능 | 정확히 아는 문구만 통과(아래 표) |
| 방어 논리 | "학습 데이터로 검증된 정확도 X%" | "값을 지어내지 않는다·실패가 투명하다" |
| 인프라 비용 | 데이터 라벨링·학습 파이프라인 | 없음(개발자가 코드로 직접 관리) |

## 처리 경로 3단 요약 (상세는 `db/document_extraction.py`)

1. **text_layer/html_text** — `pdfplumber`(PDF 전체 페이지) 또는 `beautifulsoup4`(HTML)로
   텍스트 추출 → 정규식 파싱(`db/document_text_extractor.py`)
2. **ocr** — 1이 실패하면 PaddleOCR(`db/document_ocr_extractor.py`, 100% 로컬)로 텍스트
   재구성(선형 또는 표 좌표) → **같은 정규식 파서**에 다시 흘려보냄
3. **실패** — 그마저 안 되면 `DocumentParseError` → 422, 사장님 재업로드 안내
   (실패 가시성 원칙, 자동 복구 없음)

슬롯이 지정된 업로드(위저드가 실제로 쓰는 방식)는 **제목 문구를 요구하지 않는다** —
필드 라벨(아래 표의 "필수 추출 필드" 열)만 찾으면 통과한다(2026-08-15 개선,
`db/document_text_extractor.py::_parse_with_known_slot`). "그냥 업로드"(슬롯 미지정)만
제목 문구 판별에 의존한다.

## 다음 단계 (우선순위)

실측 없이는 위 표의 "리스크·갭" 열이 전부 추측이다. 우선순위는 **실제 원본 샘플 확보**가
코드 추가보다 먼저다 — 규칙 기반 시스템의 근본적 한계(정확히 아는 문구만 통과)를
코드로는 못 없애고, 실물을 보고 규칙에 반영하는 수밖에 없다.

1. **실제 세금계산서 PDF 1장**(홈택스 다운로드, 국세청 표준 서식) — 가장 시급. 문서 유형
   1·2의 분류 키워드가 얼마나 다른지 확인
2. ~~실제 전기 고지서~~ **완료(2026-08-15)** — 사용자가 실제 한전 청구서 사진 2장을 제공,
   구조(제목·날짜 출처·금액 라벨·청구내역 표)를 확인해 반영(문서 유형 9 참고). 단, 실물
   사진 자체(스캔·촬영 화질·기울기)로는 아직 안 돌려봄 — 구조를 재현한 합성 이미지로만
   검증했다는 한계는 남음. **도시가스 고지서는 아직 미확보**(문서 유형 11)
3. **실제 관리비 고지서 1장** — 문서 유형 12, 전국 표준 서식이 없어 특히 중요
4. ~~카카오 알림톡 캡처본 1장~~ **완료(2026-08-17)** — 사용자가 실제 한전 알림톡 캡처를
   제공. 예상대로 비정형 문장형이었고, 확인 결과 애초에 계산 가능한 필드(정식 청구월·
   청구금액)가 없는 유형으로 확정 — 정규식 패턴 확장이 아니라 **항상 반려 + 방어 로직
   추가**로 마무리(문서 유형 10 참고)
5. **연료 카드영수증·LPG 영수증·거래명세서 샘플** — 문서 유형 6·7·8, 아직 실제 서식
   미확보 상태에서 표의 키워드·필드만 정의된 신규 항목
6. 샘플이 오면: 해당 문서 유형 행의 "필수 추출 필드"를 실제 문구로 갱신하고, 그 샘플을
   `tests/`에 (익명화해서) 고정 픽스처로 추가 — 이후 회귀 방지

샘플을 못 구하는 경우의 대안: 손글씨(#5)·알림톡(#10)처럼 애초에 정규식으로 감당하기
어려운 유형은, 오늘 100% 로컬로 정한 원칙을 재검토할 근거가 될 수 있다 — 그 경우
"실패율이 특히 높은 유형만" Gemini 비전을 최후 보루로 다시 붙이는 하이브리드 절충안도
있다(이전 대화에서 검토했던 옵션, §채팅 기록). 지금은 채택 안 함.

## 보류 결정 기록 (재검토 근거용)

**손글씨 합성 데이터**: 실제 손글씨 샘플이 없어 서체 폰트로 대체하는 방안을 검토했으나
보류(2026-08-15) — 폰트는 획 굵기·기울기·간격이 일정해 실제 손글씨의 난이도(불규칙성)를
대변하지 못해, 통과해도 거짓 안심만 준다고 판단. 실제 손글씨 세금계산서 샘플이 생기면
그때 다시 다룬다.

**자체 ML 문서분류 모델**: 만들지 않기로 결정(2026-08-15). 조사 근거(KB AI-OCR, 로민
