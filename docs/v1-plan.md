## 0. 현재 상태 (dev 브랜치 코드 조사 결과)

이미 완성되어 그대로 가져가는 것: 오케스트레이터 도구 7종, DB 8테이블, HITL 큐(백/프론트), PCAF 계산·벤치마킹 엔진, `/owner` 4장면.

결선에서 실제로 새로 만들어야 하는 것은 두 가지뿐이다 — 관리자 대시보드 "여신 리스크" 탭이 현재 `web/lib/admin-data.ts`의 `MOCK_RATE_CANDIDATES`, `MOCK_ALERTS` 하드코딩 배열로 되어 있다:

1. **등급 상승 역산** ("3등급→2등급에 뭐가 더 필요한지" 안내) — 백엔드 로직 전무
2. **이상 신호 알림** (여신 리스크 조짐 감지) — 백엔드 로직 전무

이 두 개를 채우는 것이 1주차 최우선 과제이고, 나머지 3주는 데이터 확장·검증·화면 반영·리허설이다.

## 1주차 (8/6 ~ 8/12) — 역산·알림 엔진

목표: 여신 리스크 탭의 목업 두 개를 실 API로 교체한다. 풀스택 2명이 각자 기능 하나씩 **API부터 화면까지 세로로 통째로** 맡는다 — 서로의 백엔드 완료를 기다리지 않도록.

| 순서 | 구현 | 검증 |

## 2주차 (8/13 ~ 8/19) — 데이터 확장·2트랙 검증

목표: 합성 전표를 결선 규모로 늘리고, 예선에서 리스트업만 해둔 백테스트를 실제로 돌려 발표용 수치 3개를 확정한다. 이번 주는 회계 검증이 병목이라, 개발자 둘은 각자 다른 축을 맡아 회계 작업을 양쪽에서 받쳐준다.

### 개발자 1 — 데이터 규모 확장

| 순서 | 구현 | 검증 |
|---|---|---|
| 1 | `db/synth_generator.py --companies 8~10`으로 300건 규모 생성 — `--count`가 아니라 `--companies`로 늘려야 함(기업당 상한 33~36건) | 생성된 전표 수·기업 분포 로그 확인 |
| 2 | 다중 기업 환경에서 `portfolio_summary` 정확성·성능 확인 (현재 로직은 N개 기업 대응 가능하나 실측 미검증) | 기업 1개 vs 10개일 때 집계 수치 정합성 대조 |
| 3 | 3주차를 위한 사전 정리 — 관리자 대시보드 컴포넌트 중 다중 기업 전환에 걸릴 만한 부분 미리 점검 (기업 셀렉터, 필터 상태 관리) | 로컬에서 기업 8~10개 목데이터로 화면 수동 전환 테스트 |

### 개발자 2 — 검증 자동화

| 순서 | 구현 | 검증 |
|---|---|---|
| 1 | 자동 평가 스크립트 작성 — 분류 정확도, 계수 매핑 정확도를 합성 전표 정답지와 자동 대조·산출 | 스크립트를 로컬에서 1회 실행해 수치 산출 확인 |
| 2 | 회계 담당의 트랙 A(MAPE 산출)를 위한 집계 헬퍼 작성 — 공시 실측치 vs 매출 추정치 비교표를 코드로 뽑아주는 스크립트 | 회계 담당이 넘긴 공시 기업 리스트로 1회 실행, 수치가 수작업 계산과 일치하는지 대조 |
| 3 | 오분류 케이스 리포트 자동 생성 (룰북 보강 대상 추출) | 회계 담당에게 전달 후 보강 반영 여부 확인 |

### 회계·도메인

| 순서 | 작업 | 검증 |
|---|---|---|
| 1 | **트랙 A** — 실측 공시 제조업체 N개에 매출액·업종만 입력하는 기존 통계 대입법(PCAF 5등급) 적용 → 공시 실측치와 비교 | 개발자 2의 집계 헬퍼로 MAPE(평균 절대 백분율 오차) 산출 |
| 2 | **트랙 B** — 합성 전표 300건 정답지 대조(분류 정확도) + 실물 파일럿 고지서 실측치 대조 | 개발자 2의 평가 스크립트로 분류 정확도 %, 실물 대조 오차 % 산출 |
| 3 | 오분류 케이스 검수 → 룰북(키워드 사전) 보강 | 보강 후 재측정 1회전 |

**2주차 완료 기준:** ① 분류 정확도 ② 트랙 A 오차율 ③ 실물 대조 오차율 — 3개 수치 확정. 90% 미달 시 데모 전표를 검증된 케이스 위주로 재구성.

## 파트별 담당 요약

풀스택 2명은 매주 다른 축으로 세로 슬라이스를 나눠 갖는다 — 특정 주에 한쪽이 다른 쪽의 백엔드/프론트를 기다리는 유휴 시간이 생기지 않도록, "이번 주 내 담당 기능은 API부터 화면까지 내가 끝까지 짠다"는 원칙을 유지한다.

| 파트 | 1주 | 2주 | 3주 | 4주 |
|---|---|---|---|---|
| **개발자 1** | 등급 역산 세로 슬라이스 (API+화면+테스트) | 데이터 규모 확장 (300건, 다중 기업 검증) | 사장님 화면 + PCAF 리포트 반영 | 리허설·병합·배포 |
| **개발자 2** | 이상 신호 알림 세로 슬라이스 (API+화면+테스트) | 검증 자동화 (평가 스크립트, 회계 집계 헬퍼) | 관리자 화면 + 트레이스 + 테스트 보강 | 리허설·병합·배포 |
| **회계·도메인** | 등급 경계값·임계값 확정 | 트랙 A/B 실행, MAPE·정확도 산출 | 발표자료, Q&A 준비 | 리허설 진행·시간 측정 |

각 주차 시작 전 15분 싱크로 "이번 주 세로 슬라이스 경계"를 서로 확인한다 — 같은 파일을 동시에 건드리는 상황을 방지하는 게 목적이지, 역할을 고정하는 게 목적이 아니다. 특정 개발자가 특정 주에 막히면(예: 회계 산출값 대기) 다른 슬라이스를 먼저 진행해도 된다.
