## 1. 문제와 목표

구미·성서공단 소부장 사장님들은 탄소중립·설비투자 관련 정부 지원사업이
있어도 존재 자체를 모르고 못 받는 경우가 많다(참고 슬라이드, 작년 iM:POSSIBLE
수상작 "항목 3: 개인화된 정부 지원사업 매칭"). 감탄은 마이데이터로 이미
기업 프로필(업종·규모·지역·중소기업 여부, `Company` 테이블 + 마이데이터 5종
`api/mydata_kyb_mock.py`)을 갖고 있으므로, 이 프로필을 기반으로 신청 가능한
지원사업을 자동으로 찾아 알려주는 것이 골자다.

이건 §1 기획서의 기존 스토리(탄소 측정 → 우대금리·설비금융 안내)와 같은
"안내 레이어"에 자연스럽게 얹힌다 — 우대금리 카드 옆에 "받을 수 있는 지원사업"
카드가 하나 더 생기는 그림. **원칙6(우대금리·설비금융 안내는 보장이 아니다)과
동일하게, 이 기능도 "신청 후보 안내"이지 "선정 보장"이 아니다.**

## 2. 스코프 (v1 결선 — Tier 2)

**한다**:
- 기업마당(정부 지원사업 정보) 실 API 연동, 탄소중립·설비투자 관련 사업만 필터
- 기업 프로필 기반 매칭(벡터 유사도) + LLM 근거 문장 생성
- 사장님 화면에 매칭 결과 카드 노출(신청 링크·마감일 포함)

**안 한다** (v1 제외):
- 신청서 자동 작성·자동 제출 대행
- 선정 여부 예측·확률 점수화(고영향 AI 영역 — 원칙6과 동일 이유로 회피)
- 정부 지원사업 외 다른 유형(세제 혜택, 지자체 조례 등)까지 확장

## 3. 데이터 소스 — 기업마당(bizinfo.go.kr) 지원사업정보 API

**기업마당(bizinfo.go.kr) 자체 지원사업정보 API**를 1차 소스로 쓴다(공공데이터
포털 경유가 아니라 bizinfo.go.kr이 직접 발급·서비스하는 API — 2026-08-18 확인,
아래 신청 방법 참고). REST 기반 JSON/XML, 필드는 분야·사업명·신청시작일자·
신청종료일자·소관기관·수행기관·접수기관·등록일자·상세URL 등 — 정형 필드에는
"업종/지역/규모 신청 자격"이 구조화돼 있지 않고 상세페이지 본문(비정형
텍스트)에 섞여 있을 가능성이 높다. **이게 벡터 검색(RAG)이 필요한 이유** —
"제조업, 상시근로자 50인 미만, 대구·경북 소재 기업 우대" 같은 조건은
정형 필터로 못 거르고 본문 임베딩 유사도로 걸러야 한다.

- 출처: [기업마당 지원사업정보 API 안내](https://www.bizinfo.go.kr/apiDetail.do?id=bizinfoApi)
  (호출 엔드포인트 `https://www.bizinfo.go.kr/uss/rss/bizinfoApi.do`). 참고용
  분기 스냅숏: [공공데이터포털 중소기업지원사업목록](https://www.data.go.kr/data/3034791/fileData.do)
  (파일 데이터, 실시간 아님 — 배치 소스로 안 씀).
- **선행 작업(지금 바로 시작해야 함)**: ~~공공데이터포털 활용신청~~ →
  **bizinfo.go.kr API 안내 페이지에서 직접 등록 신청**(기관/회사명·신청자명·
  이메일·전화번호·시스템명·시스템 IP주소 또는 URL 입력) → 승인 시 이메일로
  인증키(`crtfcKey`) 발급, 통상 몇 시간~1일 소요. 결선 일정이 임박했으니 이
  문서 확정과 무관하게 신청부터 먼저 넣는 걸 권장. 신청서의 "시스템 IP주소
  또는 URL"은 배치 스크립트를 GitHub Actions에서 돌릴 예정이라 고정 IP가
  없음 — 신청 시 그렇게 기재하거나 개발 로컬 정보로 우선 넣고 승인 후
  문제 시 재문의.
- 데이터 신선도: 지원사업 공고는 상시 갱신되므로 실시간 호출이 아니라
  **배치 수집**(1일 1회, GitHub Actions — 이미 Supabase ping 용도로 쓰는
  스케줄러 재사용 가능)으로 로컬 테이블에 캐시한다. 실시간 API 직접 호출은
  응답 지연·요청 한도 문제로 사용자 화면 경로에 넣지 않는다.
- **필터링 (2026-08-18 정정, 2차 정정)**: 원래 "분야 코드(환경/에너지)로
  1차 필터"를 계획했으나, 실제 API의 `searchLclasId`(분야 코드)는 01 금융·
  02 기술·03 인력·04 수출·05 내수·06 창업·07 경영·09 기타 8개뿐 —
  환경·에너지·탄소 전용 분야가 없다. 처음엔 대안으로 `hashtags` 파라미터
  1차 필터 + 로컬 키워드 2차 확인을 계획했으나, **실측 결과 `hashtags`
  사전 필터는 뺐다** — 이유:
  1. hashtags 자체가 정밀하지 않다(탄소·설비 무관 공고가 섞여 나옴)
  2. 더 중요한 문제: hashtags로 먼저 좁히면, 우리가 지정한 단어와 겹치는
     태그가 하나도 없는 진짜 관련 공고가 애초에 후보 풀에 들어오지도
     못하고 통째로 누락된다(재현율 손실)
  3. 그런데 `searchCnt` 파라미터에 큰 값(2000)을 주면 **전체 공고
     (2026-08-18 기준 1524건)가 페이지네이션 없이 한 번의 호출로 다
     온다** — 굳이 hashtags로 먼저 좁일 이유가 없다.

  **최종 설계: 매일 전체 공고를 한 번에 가져와서(`searchCnt` 크게) 로컬
  키워드만으로 포함 여부를 결정**한다. 키워드: 탄소, 그린, 온실가스,
  탄소중립, 탄소저감, 저탄소, 배출권, 배출량, 설비투자, 설비교체,
  노후설비, 에너지효율, 에너지진단, RE100, 친환경, ESG, 클린팩토리 —
  대상 텍스트는 `pblancNm`(공고명)·`bsnsSumryCn`(사업개요, HTML 태그
  제거)·`trgetNm`(지원대상). 전체가 1500건대라 API 호출·로컬 필터링
  비용 모두 무시할 수준이라, "비용 절감용 사전 필터"라는 원래 목적
  자체가 이 규모에서는 불필요했다.

  **잔여 위험(2026-08-18 인지, 의도적으로 수용)**: 키워드 방식은 구조적으로
  목록에 없는 표현(예: 넷제로, CBAM, 기후테크, 재생에너지, 그린뉴딜,
  탄소배출권거래제 등)을 쓰는 공고를 놓친다 — 아무리 목록을 늘려도
  근본적으로 없앨 수 없는 한계. 완화책으로 "키워드 미매칭 공고 제목만
  Gemini에 배치로 보내 재판별"(전표 분류의 룰 우선→애매한 것만 LLM 원칙과
  동일한 결)을 검토했으나, 결선 일정 압박으로 **지금은 키워드 방식만으로
  진행하고 이 위험을 감수하기로 결정**. 나중에 여유가 되면 이 LLM 안전망
  단계를 §6-3 사이에 추가하는 걸로 확장 가능(코드 구조를 바꾸는 게 아니라
  필터링 단계 하나를 끼워 넣는 정도라 나중 추가가 어렵지 않음).

## 4. 아키텍처

```
[배치] scripts/fetch_gov_support_programs.py (1일 1회, 신규/변경분만)
   ↓
bizinfo.go.kr 지원사업정보 API(crtfcKey) → 1차 키워드 필터 → gov_support_programs 테이블 upsert
   ↓
신규/변경 행만 임베딩 재생성(google-genai) → pgvector 컬럼에 저장
   ↓
[요청 시] 사장님이 리포트/혜택 화면 진입
   → **지역 자격 하드 필터(§6-5)** — company.region이 program.region_tags에
     없고 전국 사업도 아니면 유사도 계산 전에 제외 (결정론적, 임베딩 안 씀)
   → 남은 후보만 기업 프로필 텍스트(업종명·지역·종업원수·연료유형) 쿼리 임베딩
   → 벡터 유사도 top-K(예: 5) 검색 — 결정론적 코사인 유사도 계산
   → 유사도 임계값 미만 전부 제외(원칙9와 같은 결 — 억지로 채우지 않음)
   → LLM(Gemini)이 상위 후보 각각에 대해 "왜 이 회사에 맞는지" 1~2문장 생성
   → 사장님 화면에 카드로 노출(사업명·마감일·소관기관·근거문장·상세URL)
```

**LLM 산수 금지 원칙과의 정합성(원칙1과 동일한 결)**: 매칭 자체(어떤 사업이
상위로 올라오는지)는 임베딩 코사인 유사도라는 결정론적 계산이 결정한다.
LLM은 이미 골라진 후보에 대해 "왜 맞는지" 설명 문장만 생성하고, 그 설명이
잘못돼도 노출되는 사업 목록 자체는 안 바뀐다 — "환각이 매칭 결과에 개입할
경로가 없다"는 방어 논리를 여기서도 유지한다. 마감일·소관기관 등 사실
필드는 API 원문 그대로 노출하고 LLM이 재작성하지 않는다.

## 5. 기술 선택 — 공유 Postgres에 JSON 저장 + Python 코사인 유사도 (2026-08-18 최종 확정, pgvector에서 정정)

처음엔 `pgvector` 확장(Supabase가 기본 지원)을 확정했으나, **구현 착수
직전 실제 충돌을 발견해 정정**했다 — 이 프로젝트의 테스트 전체가
SQLite(`tmp_path` 인메모리, `tests/pcaf_engine/test_rate_products.py` 등
모든 기존 테스트 파일이 동일 패턴)로 도는데, pgvector의 SQLAlchemy `Vector`
컬럼 타입은 Postgres 전용이라 SQLite에서 테이블 생성 자체가 깨진다. 이
테이블만 예외적으로 실제 Postgres가 있어야 테스트되게 만들면 기존 테스트
관행과 어긋나고 새 테스트 인프라(Postgres 컨테이너·conftest 분기)가 필요해진다.

**최종 결정**: `embedding` 컬럼을 `vector` 타입이 아니라 **`JSON`(float
리스트)**으로 저장하고, 코사인 유사도는 SQL 연산자가 아니라 **매칭 함수
안에서 Python으로 계산**한다. 여전히 공유 Supabase Postgres에 저장되므로
"팀 공유 DB 원칙"(아래 표 FAISS 비교)은 그대로 지켜지고, SQLite·Postgres
양쪽에서 동일하게 동작해 기존 테스트 패턴을 그대로 쓸 수 있다. 데이터
규모(수백 건)에서 Python 루프 코사인 계산은 성능 문제가 안 된다 — 애초에
§5 이전 버전도 "이 규모에서 IVFFlat/HNSW 인덱스 불필요, 순차 스캔으로
충분"이라고 판단했었다(즉 pgvector를 골랐던 이유였던 "DB 네이티브 ANN
검색 성능"은 원래도 이 규모에서 크게 필요하지 않았다).

| | FAISS(로컬 인덱스 파일) | JSON + Python 코사인(최종 채택) |
| --- | --- | --- |
| 인프라 | 로컬 인덱스 파일, Docker 볼륨 관리 필요 | 기존 Supabase Postgres에 컬럼 하나 추가(`JSON` 타입, 이미 다른 테이블에서도 쓰는 흔한 타입) |
| 팀 공유 DB 원칙과의 정합성 | 인덱스 파일이 컨테이너별로 따로 놀 위험(§3 "공유 DB" 원칙과 충돌) | 이미 공유 DB에 저장 — 여러 명이 동시에 봐도 항상 최신 |
| 마이그레이션 | 해당 없음(파일 기반) | Alembic revision으로 관리(§3 규칙 그대로 적용 가능) |
| 테스트 | 해당 없음 | 기존 SQLite 테스트 패턴 그대로 재사용 — 새 인프라 불필요 |

`pgvector` 파이썬 패키지·Postgres `vector` 익스텐션 모두 **불필요** —
CLAUDE.md §3 기술스택 표도 이 결정으로 갱신했다. 임베딩 생성 자체는
기존 계획대로 `google-genai` 임베딩 API를 쓴다(전표 분류에 이미 쓰는
것과 같은 SDK, 새 프로바이더 안 늘림).

## 6. DB 스키마 (Alembic 신규 revision, 확정안)

```
gov_support_programs
  id                Integer PK
  source            String(30) NOT NULL, default 'bizinfo'
  external_id       String(50) NOT NULL   # API 원본 공고 ID (bizinfo pblancId)
  program_name      String(200) NOT NULL
  category          String(50)            # 분야명 (분야 코드가 아니라 코드명 그대로 저장 — §3-1)
  agency_name       String(100)           # 소관기관
  apply_start_date  Date, nullable        # 파싱 성공 시만 채움
  apply_end_date    Date, nullable        # 파싱 성공 시만 채움 — 미확정(예산 소진시까지 등)이면 null
  apply_period_raw  String(100)           # 원문 그대로 보관 — "모집 완료시"·"예산 소진시까지" 등
                                           # 날짜로 안 파싱되는 값이 실제로 존재함(2026-08-18 실측 확인)
  region_tags       String(200), nullable # hashtags에서 뽑은 지역명 콤마 목록. null/전국 판정은 §6-5
  detail_url        String(500)
  raw_text          Text                  # 임베딩 대상 원문(사업개요+지원대상 조합, HTML 태그 제거)
  raw_text_hash     String(64)            # sha256(raw_text) — 변경분만 재임베딩 판단
  embedding         JSON, nullable        # float 리스트(768차원), §5·§6-1 — pgvector Vector 타입 아님
  is_active         Boolean NOT NULL default true  # 최신 배치에서 안 보이면 false
  fetched_at        DateTime(timezone=True)  # 마지막 성공 수집 시각 — §7 "O일 전 기준" 문구용
  updated_at        DateTime(timezone=True)
  created_at        DateTime(timezone=True)

  UNIQUE (source, external_id)
  INDEX  (is_active, apply_end_date)   # 마감 지난 공고 제외 조회용
```

**마감일 필터링 시 주의**: `apply_end_date`가 null인 행(파싱 실패·상시모집)을 실수로
"마감됨"으로 취급해 제외하면 안 된다 — null은 "마감일 모름/상시"로 해석해 후보에
남긴다. `WHERE apply_end_date IS NULL OR apply_end_date >= CURRENT_DATE`.

기존 테이블 22개와 별개 신규 테이블 — `db/models.py` 추가 후 새 revision.
기업별 매칭 결과는 저장하지 않고 매 조회 시 재계산한다(원칙8 "승인된 값만
버전 관리" 대상이 아님 — 이건 추천일 뿐 승인·확정 개념이 없음).

`embedding` 컬럼은 SQLAlchemy `JSON` 타입(float 리스트) — §5 정정으로
`pgvector` 파이썬 패키지·Postgres `vector` 익스텐션 둘 다 안 쓴다. 코사인
유사도는 매칭 함수(`db/gov_support/matching.py`) 안에서 순수 Python으로
계산 — 수백 건 규모에서 성능 문제 없음.

### 6-1. 임베딩 모델

**`gemini-embedding-2`**(2026-08-18 기준 Gemini 최신 임베딩 모델, `gemini-embedding-001`
후속 — 텍스트 8,192토큰까지 지원, 001은 2,048토큰 한도라 지원사업 상세 요약문엔
빠듯할 수 있어 신모델 채택). `output_dimensionality=768`로 truncate(공식 권장값
768/1536/3072 중 최소값 — 이 프로젝트 규모에서 저장공간·속도가 정확도보다
아쉬울 이유가 없어 가장 가벼운 값 선택). 두 모델의 임베딩 공간이 호환되지
않으므로 처음부터 gemini-embedding-2로 통일하고 절대 섞지 않는다.

비대칭 검색(저장문서 vs 조회쿼리)이라 `task_type`을 구분해서 호출한다 —
배치가 `raw_text`를 임베딩할 땐 `RETRIEVAL_DOCUMENT`, 요청 시 기업 프로필
쿼리를 임베딩할 땐 `RETRIEVAL_QUERY`. 같은 텍스트라도 task_type이 다르면
임베딩 값이 달라지므로 두 경로에서 절대 바꿔 쓰지 않는다.

### 6-2. API 계약

`GET /owner/{company_id}/gov-support-candidates` (`api/routers/owner.py` 추가)

```json
{
  "as_of": "2026-08-17",
  "candidates": [
    {
      "program_id": 123,
      "program_name": "탄소중립 설비투자 지원사업",
      "agency_name": "대구광역시",
      "apply_end_date": "2026-09-30",
      "detail_url": "https://www.bizinfo.go.kr/...",
      "similarity": 0.83,
      "evidence": "제조업·대구 소재·상시근로자 50인 미만 조건에 부합"
    }
  ]
}
```

- `as_of`는 `fetched_at` 기준 — 배치가 실패해 오래된 캐시를 그대로 쓰는 경우
  화면에서 "O일 전 기준" 문구를 만들 때 씀(§7).
- `evidence`가 `null`이면 LLM 근거 생성 실패 — 프론트가 "설명 생성 실패"로
  표기(대체 문구로 안 가림, §7).
- `candidates`가 빈 배열이면 화면에서 "현재 조건에 맞는 지원사업이 없어요".
- `apply_end_date`가 지났거나 `is_active=false`인 공고는 쿼리 단계에서 제외.

### 6-3. 배치 스크립트

`scripts/fetch_gov_support_programs.py` — `scripts/fetch_industry_distributions.py`와
같은 독립 실행 스크립트 스타일(urllib, `load_dotenv()`)이되, 그 스크립트는
정적 스냅숏(xlsx)을 만들지만 이 스크립트는 지원사업 마감일이 실시간성이 있어
**DB에 직접 upsert**한다 — `api/db.py::get_engine()`을 그대로 재사용해 커넥션
풀 설정(pool_size=3)을 이원화하지 않는다.

```
1. bizinfo API 호출 (BIZINFO_API_KEY) — `searchCnt`를 넉넉히 크게 줘서
   (예: 3000) 전체 공고를 페이지네이션 없이 한 번에 가져온다(§3 실측:
   1524건 전체가 한 호출로 옴). hashtags 사전 필터는 안 쓴다(§3 정정 —
   재현율 손실 위험).
2. 응답의 `pblancNm`·`bsnsSumryCn`·`trgetNm` 텍스트로 로컬 키워드 필터
   (§3 키워드 목록) — 여기서 안 걸리면 후보에서 제외. 이 필터가 유일한
   포함 여부 결정 기준이다.
3. (source, external_id) 기준 기존 행 조회
   - 신규: insert, raw_text_hash 계산, hashtags에서 지역 토큰 추출해
     region_tags 저장(§6-5)
   - 기존: raw_text_hash 비교 — 다르면 update + 재임베딩 대상 표시,
     같으면 raw_text_hash까지만 확인하고 임베딩 재호출 안 함(비용 절감,
     llm_cache의 "동일 텍스트→동일 응답" 원칙과 같은 결). region_tags는
     매번 갱신(해시 비교 대상 아님 — 값이 작아 재계산 비용 무시 가능)
   - 이번 배치에 안 보인 기존 행: is_active=false (하드 delete 안 함,
     마감·중단된 공고 이력 보존)
4. 재임베딩 대상만 gemini-embedding-2 호출 (RETRIEVAL_DOCUMENT) → embedding 갱신
5. fetched_at 갱신은 배치 전체가 부분 실패해도 "이번에 성공적으로 처리된 행"
   기준으로만 — 실패한 행은 이전 fetched_at 유지(실패 가시성 원칙)
```

GitHub Actions는 `.github/workflows/ping-db.yml`과 같은 저장소에 새 워크플로우
파일로 추가(`fetch-gov-support.yml`), `schedule: cron: "30 1 * * *"`(Supabase
핑 10분 뒤, KST 10:30) + `workflow_dispatch`로 수동 실행도 허용. `BIZINFO_API_KEY`·
`GEMINI_API_KEY`·`DATABASE_URL`을 GitHub Secrets로 등록해야 함(이것도 사용자가
직접 해야 하는 액션 아이템).

### 6-4. 유사도 임계값·top-K 튜닝

`match_gov_support_programs(session, company_id, *, top_k=5, similarity_threshold=0.60)`
처럼 상수 대신 함수 인자(기본값 포함)로 받는다 — 나중에 값이 바뀌어도 매칭
로직 코드는 안 건드리고 호출부·기본값만 바꾸면 된다(§6-2 API가 이 함수를
기본값 그대로 호출).

**담당(2026-08-18 변경)**: 애초 회계·도메인이 직접 여러 값을 실험할 계획이었으나,
실 데이터 확보 후 튜닝 스크립트(`scripts/tune_gov_support_threshold.py`) 작성·
실행까지 구현 단계에서 함께 처리하기로 함 — bizinfo 배치로 실제 지원사업이
쌓이면 시연 기업 프로필로 top_k·threshold 여러 조합을 돌려 결과를 표로
뽑고, 그 표를 회계·도메인이 최종 검토(그럴듯한 사업이 상위에 오는지, 엉뚱한
게 안 섞이는지)해서 기본값을 확정하는 순서로 진행. 직접 값을 실험하는
부담은 회계·도메인에게 지우지 않는다.

**초기값 확정(2026-08-18, 튜닝 스크립트 1차 실행 결과)**: 시연 기업(구미정밀,
경북 구미, 기타 금속가공제품 제조)으로 실행한 결과 `threshold=0.65`는
진짜 관련 있는 사업(에너지효율 혁신 선도 프로젝트 0.6283, EU CBAM 대응
컨설팅 0.6265, 온실가스 국제감축사업 0.6169, 다공성 탄소소재 환경소재
0.6086 등)을 전부 걸러내고 일반 경쟁력강화 자금 지원 2건만 남겼다.
`threshold=0.60`으로 낮추면 21건이 통과하고 상위권이 실제로 그럴듯하다 —
`DEFAULT_SIMILARITY_THRESHOLD`를 0.60으로 변경. **이 초기값도 회계·도메인의
최종 검토 전까지는 잠정치**로 취급한다(구미정밀 1개 기업 기준이라 다른
업종·지역 기업으로도 확인 필요).

### 6-5. 지역 자격 하드 필터 (2026-08-18 실측으로 발견·추가)

**발견**: 최근 300건 키워드 매칭 실측 결과, "관련성 높다"고 판단한 상위
후보 대부분이 실제로는 특정 타 지역(경기·울산·인천 등) 소재 기업 전용
공고였다 — `hashtags` 필드에 지역명이 담겨 있는데, 지역 토큰이 1개면
그 지역 한정, 16개(사실상 전체 지역)면 전국 대상(주로 중앙부처 사업)인
패턴이 뚜렷했다. 지역 자격은 "제조업·중소기업" 같은 주제 유사도와는
성격이 다른 **하드 조건(이 조건 불충족이면 유사도가 아무리 높아도
신청 자체가 불가능)**이라, §1 원칙("LLM 산수 금지"와 같은 결 — 결정론적으로
판단 가능한 건 임베딩 유사도라는 퍼지 매칭에 맡기지 않는다)에 따라
임베딩 유사도 계산 전에 코드로 확정 배제한다.

**판정 규칙**:
```
region_tags가 없음(null)                     → 통과 (지역 태그 자체가 없는 경우, 배제하지 않고 안전하게 포함)
region_tags 토큰 수 >= 10                     → 통과 (전국 사업으로 간주 — 2026-08-18 실측 기준 1개 vs 16개로
                                                  뚜렷이 양분되어 있어 여유를 둔 임계값)
company.region이 region_tags에 포함 → 통과 (실측 확인: `Company.region`은 이미
                                                  "경북 구미"·"경북 경산" 형식이라 앞 토큰만
                                                  떼면 됨 — 별도 지역 코드 매핑 테이블 불필요)
그 외                                          → 제외
```

**캐치**: 이 판정은 `hashtags`가 각 소관기관이 등록할 때 채워 넣는 값이라
완벽히 정확하다는 보장은 없다(수기 등록 데이터의 일반적 한계) — 최선의
구조화 신호이지 권위 있는 원천은 아니다. 배치 스크립트가 그대로
`region_tags`에 저장만 하고 판정 로직(위 규칙)은 매칭 함수 쪽에 둬서,
나중에 임계값(10)이나 정규화 매핑을 조정해도 재수집 없이 반영되게 한다.

### 10-1. 중소벤처24 (2026-08-18, 키 신청만 병행)

정식 명칭 "중소기업기술정보진흥원_중소벤처24 공고정보"
([data.go.kr](https://www.data.go.kr/data/15113191/openapi.do)). bizinfo와
달리 진짜 공공데이터포털 경유가 맞고, 개발계정은 자동승인이라 신청이 간단함
— 그래서 실제 구현 여부와 무관하게 키 신청만 지금 넣어두기로 함(리드타임
확보). `.env.example`에 `SMES24_API_KEY` 자리 추가.

**아직 구현 안 함**: bizinfo와 데이터가 겹치는지 불확실(둘 다 중소벤처기업부
계열 공고를 모음) — 실제 호출로 겹침 여부를 확인하는 작업과, `source`
컬럼 구분·중복 제거 로직 추가가 필요해 v1 스코프 밖으로 유지. 키만 미리
확보해 나중에 필요하면 바로 시작할 수 있게 함.

### 10-2. 기술보증기금 (2026-08-18, 결론: 별도 소스 아님)

기술보증기금은 지원사업 매칭 파이프라인에 새 소스로 추가하지 않는다 — 실측
확인 결과 두 갈래로 이미 처리됨:

- **시한부 공고성 지원사업**(예: 기보벤처캠프, M&A 컨설팅)은 기술보증기금이
  수행기관으로 참여하면 bizinfo에 이미 올라오고, 우리 배치가 그대로
  잡아낸다(실측: bizinfo 1524건 중 기술보증기금 수행 4건 확인). 별도
  연동 불필요.
- **상시 운영 보증상품**(녹색보증·탄소중립 협약보증 등)은 KIBO 자체
  오픈API에 그런 데이터가 없고(확인됨 — 있는 API는 기술이전 DB·통계뿐),
  bizinfo류 "공고" API 구조에도 안 맞는다(마감일 있는 공고가 아니므로).
  API 자동화 경로가 없다 — 다만 실측 중 "2026년 무탄소에너지보증사업
  (해상풍력 맞춤형 보증지원)"(기후에너지환경부/한국에너지공단)처럼
  **보증기관이 공고 형태로 올리는 사례가 실제로 존재**해서, 향후
  기술보증기금이 같은 방식으로 올리면 별도 작업 없이 자동 포착된다.
- 웹 스크래핑으로 KIBO 홈페이지의 상시 상품을 긁어오는 안은 검토했으나
  **채택하지 않음** — 이 프로젝트의 다른 모든 데이터 소스는 공식 API
  기반인데 스크래핑만 비공식·페이지 구조 변경에 취약해 안정성이 떨어짐.
  결선 임박 상황에서 새 불안정 요소를 들이는 리스크가 이득보다 크다고 판단.
- 상시 보증상품을 화면에 노출하고 싶다면, `RateProduct` 테이블에 iM뱅크
  상품(`db/init_db.py` 기존 2건)과 같은 패턴으로 사람이 직접 조사해
  넣는 방식을 쓴다 — 착수 여부는 미정(사용자 확인 대기).
