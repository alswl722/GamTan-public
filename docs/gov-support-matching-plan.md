# 개인화된 정부 지원사업 매칭 — 기획안 (Tier 2, 결정 대기)

> 진행 상태·완료조건 체크는 `docs/v1-plan.md` §5(남은 항목)가 정본. 이 문서는
> 이 기능의 배경·데이터소스·아키텍처를 상세히 남기는 기획 문서다. 아직 팀
> 확정 전 — §7 "미결정 사항"이 승인되기 전까지는 CLAUDE.md §3 기술스택 표에
> 반영하지 않는다.

## 1. 문제와 목표

구미·성서공단 소부장 사장님들은 탄소중립·설비투자 관련 정부 지원사업이
있어도 존재 자체를 모르고 못 받는 경우가 많다(참고 슬라이드, 작년 iM:POSSIBLE
수상작 "항목 3: 개인화된 정부 지원사업 매칭"). 감탄은 마이데이터로 이미
기업 프로필(업종·규모·지역·중소기업 여부, `Company` 테이블 + 마이데이터 5종
`api/mydata_kyb_mock.py`)을 갖고 있으므로, 이 프로필을 기반으로 신청 가능한
지원사업을 자동으로 찾아 알려주는 것이 골자다.

이건 §1 기획서의 기존 스토리(탄소 측정 → 우대금리·설비금융 안내)와 같은
"안내 레이어"에 자연스럽게 얹힌다 — 우대금리 카드 옆에 "받을 수 있는 지원사업"
카드가 하나 더 생기는 그림. **원칙6(우대금리·설비금융 안내는 보장이 아니다)과
동일하게, 이 기능도 "신청 후보 안내"이지 "선정 보장"이 아니다.**

## 2. 스코프 (v1 결선 — Tier 2)

**한다**:
- 기업마당(정부 지원사업 정보) 실 API 연동, 탄소중립·설비투자 관련 사업만 필터
- 기업 프로필 기반 매칭(벡터 유사도) + LLM 근거 문장 생성
- 사장님 화면에 매칭 결과 카드 노출(신청 링크·마감일 포함)

**안 한다** (v1 제외):
- 신청서 자동 작성·자동 제출 대행
- 선정 여부 예측·확률 점수화(고영향 AI 영역 — 원칙6과 동일 이유로 회피)
- 정부 지원사업 외 다른 유형(세제 혜택, 지자체 조례 등)까지 확장

## 3. 데이터 소스 — 기업마당(bizinfo.go.kr) 지원사업정보 API

공공데이터포털(data.go.kr)에 개방된 **중소벤처기업부 기업마당 지원사업정보
API**를 1차 소스로 쓴다. REST 기반 JSON/XML, 필드는 분야·사업명·신청시작일자·
신청종료일자·소관기관·수행기관·접수기관·등록일자·상세URL 등 — 정형 필드에는
"업종/지역/규모 신청 자격"이 구조화돼 있지 않고 상세페이지 본문(비정형
텍스트)에 섞여 있을 가능성이 높다. **이게 벡터 검색(RAG)이 필요한 이유** —
"제조업, 상시근로자 50인 미만, 대구·경북 소재 기업 우대" 같은 조건은
정형 필터로 못 거르고 본문 임베딩 유사도로 걸러야 한다.

- 출처: [기업마당 지원사업정보 API](https://www.bizinfo.go.kr/apiDetail.do?id=bizinfoApi), [공공데이터포털 중소기업지원사업목록](https://www.data.go.kr/data/3034791/fileData.do)
- **선행 작업(지금 바로 시작해야 함)**: 공공데이터포털 회원가입 + 활용신청 →
  API 키 발급까지 보통 몇 시간~1일 소요. 결선 일정이 임박했으니 이 문서
  확정과 무관하게 신청부터 먼저 넣는 걸 권장.
- 데이터 신선도: 지원사업 공고는 상시 갱신되므로 실시간 호출이 아니라
  **배치 수집**(1일 1회, GitHub Actions — 이미 Supabase ping 용도로 쓰는
  스케줄러 재사용 가능)으로 로컬 테이블에 캐시한다. 실시간 API 직접 호출은
  응답 지연·요청 한도 문제로 사용자 화면 경로에 넣지 않는다.
- 필터링 1차: 기업마당 API의 `분야` 코드(환경/에너지 등) + 키워드
  (탄소, 그린, 온실가스, 탄소중립, 설비투자, 에너지효율, RE100 등)로
  전체 지원사업 중 관련 후보만 추린다 — 전체를 다 임베딩하지 않는다
  (비용·정확도 둘 다 이유).

## 4. 아키텍처

```
[배치] scripts/fetch_gov_support_programs.py (1일 1회, 신규/변경분만)
   ↓
공공데이터포털 API → 1차 키워드 필터 → gov_support_programs 테이블 upsert
   ↓
신규/변경 행만 임베딩 재생성 → 인덱스 저장(§5 기술선택)
   ↓
[요청 시] 사장님이 리포트/혜택 화면 진입
   → 기업 프로필 텍스트(업종명·지역·종업원수·연료유형) 쿼리 임베딩
   → 벡터 유사도 top-K(예: 5) 검색 — 결정론적 코사인 유사도 계산
   → 유사도 임계값 미만 전부 제외(원칙9와 같은 결 — 억지로 채우지 않음)
   → LLM(Gemini)이 상위 후보 각각에 대해 "왜 이 회사에 맞는지" 1~2문장 생성
   → 사장님 화면에 카드로 노출(사업명·마감일·소관기관·근거문장·상세URL)
```

**LLM 산수 금지 원칙과의 정합성(원칙1과 동일한 결)**: 매칭 자체(어떤 사업이
상위로 올라오는지)는 임베딩 코사인 유사도라는 결정론적 계산이 결정한다.
LLM은 이미 골라진 후보에 대해 "왜 맞는지" 설명 문장만 생성하고, 그 설명이
잘못돼도 노출되는 사업 목록 자체는 안 바뀐다 — "환각이 매칭 결과에 개입할
경로가 없다"는 방어 논리를 여기서도 유지한다. 마감일·소관기관 등 사실
필드는 API 원문 그대로 노출하고 LLM이 재작성하지 않는다.

## 5. 기술 선택 — 미결정 (팀 확인 필요)

CLAUDE.md §3 기술스택 표에는 벡터 검색 관련 항목이 없다. 참고 슬라이드는
FAISS(로컬 파일 인덱스)를 썼지만, 이 프로젝트는 이미 Supabase(PostgreSQL)를
팀 공유 DB로 쓰고 있어 별도 벡터 인덱스 파일을 앱 컨테이너에 들고 다니는
FAISS보다 **`pgvector` 확장(Supabase가 기본 지원)이 이 아키텍처에 더 맞을
가능성이 높다** — 이유:

| | FAISS | pgvector |
| --- | --- | --- |
| 인프라 | 로컬 인덱스 파일, Docker 볼륨 관리 필요 | 기존 Supabase Postgres에 컬럼 하나 추가(`vector` 타입) |
| 팀 공유 DB 원칙과의 정합성 | 인덱스 파일이 컨테이너별로 따로 놀 위험(§3 "공유 DB" 원칙과 충돌) | 이미 공유 DB에 저장 — 여러 명이 동시에 봐도 항상 최신 |
| 마이그레이션 | 해당 없음(파일 기반) | Alembic revision으로 관리(§3 규칙 그대로 적용 가능) |
| 참고 슬라이드와의 일치도 | 슬라이드 원안과 동일 | 슬라이드 컨셉은 유지하되 구현만 다름 |

**권장: pgvector.** 다만 이건 CLAUDE.md §3 "확정 — 변경 금지" 표에 새 행을
추가하는 결정이라 팀 확인 후 CLAUDE.md에 반영해야 한다(이 문서 자체는
아직 그 반영을 하지 않음 — 위 안내 문구 참고).

## 6. DB 스키마안 (Alembic 신규 revision 필요)

```
gov_support_programs
  id, source (bizinfo 등), external_id(API 원본 ID, 재수집 시 upsert 키)
  program_name, category, agency_name, apply_start_date, apply_end_date,
  detail_url, raw_text(본문 요약, 임베딩 대상), embedding vector(pgvector면),
  fetched_at, updated_at
```

기존 테이블 22개와 별개 신규 테이블 — `db/models.py` 추가 후 새 revision.
기업별 매칭 결과는 저장하지 않고 매 조회 시 재계산한다(원칙8 "승인된 값만
버전 관리" 대상이 아님 — 이건 추천일 뿐 승인·확정 개념이 없음).

## 7. 실패 가시성 원칙 적용

- API 배치 수집 실패 시: 마지막 성공 시점 캐시를 그대로 쓰되, 화면에 "지원사업
  정보가 O일 전 기준"임을 명시(실패를 숨기지 않음, CLAUDE.md §6과 동일 결).
- 임베딩/LLM 근거 생성 실패 시: 사업 카드는 노출하되(사실 필드는 API 원문이라
  안전) 근거 문장 자리에 "설명 생성 실패"를 표시 — 대체 문구로 가리지 않는다.
- 매칭 결과 0건이면 "현재 조건에 맞는 지원사업이 없어요"를 명시(억지로 채우지
  않음, 원칙9와 같은 결).

## 8. 화면 배치

사장님 앱의 "혜택" 페이지(`web/app/owner/benefits`, 기존 우대금리·설비금융
카드가 있는 곳)에 세 번째 카드 유형으로 추가 — 이미 있는 안내 레이어 UI
패턴(비보장 문구 disclaimer 포함)을 그대로 재사용한다.

## 9. 담당·일정

개발자 A(사장님 플로우) 담당이 적합 — 하이브리드 데이터 입력·안내 레이어를
이미 맡고 있어 기업 프로필 소스(§3 마이데이터)와 화면 배치(§8) 둘 다 이미
익숙하다. 배치 수집 스크립트(§4)는 회계·도메인이 관리하는 `data/*.xlsx`
갱신 패턴과 달리 코드로 자동화되는 부분이라 개발자 A가 직접 작성.

**일정 리스크**: `docs/v1-plan.md` 기준 결선이 임박했고(3주차 통합테스트·
4주차 기능동결 남음), Tier 1(검증 3수치)이 아직 완료 전이다. 이 기능은
API 키 신청 리드타임 + 신규 인프라(벡터 검색) 학습곡선이 있어 **일정
경합이 실제로 있다** — §5 기술 선택과 착수 시점을 팀이 먼저 확정해야
`docs/v1-plan.md` §4/§5 표에 정식으로 옮길 수 있다.

## 10. 미결정 사항 (팀 확인 전 착수 금지)

1. FAISS vs pgvector — §5, CLAUDE.md §3 반영 필요
2. 착수 시점 — Tier 1 검증 수치 완료 전/후 중 언제 시작할지
3. 기업마당 API 외 추가 소스(중소벤처24, 지자체 개별 공고) 포함 여부 —
   v1은 기업마당 단일 소스로 좁히는 걸 권장(범위 통제)
4. 유사도 임계값·top-K 값 — 데모 시연 시 "그럴듯한 사업이 안 뜨는" 리스크를
   회계·도메인이 실제 지원사업 목록으로 사전 검증 필요
